# ACID Properties in DBMS

## 1. What is ACID?

**ACID** is a set of four properties that ensure **database transactions are processed reliably and correctly**.

ACID stands for:

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

These properties are especially important in systems where data must remain correct even when:

* A transaction fails
* The application crashes
* The server goes down
* Multiple users access the database simultaneously
* A power failure occurs
* Network problems occur

### Simple Definition

> **ACID properties ensure that database transactions are reliable, consistent, isolated from one another, and permanently saved after successful completion.**

---

# 2. What is a Transaction?

Before understanding ACID, we need to understand a **transaction**.

A transaction is a sequence of one or more database operations that together represent **one logical unit of work**.

For example, transferring ₹1,000 from Account A to Account B requires two operations:

```text
1. Deduct ₹1,000 from Account A
2. Add ₹1,000 to Account B
```

These two operations together form **one transaction**.

```text
Transaction
    |
    ├── Debit Account A
    |
    └── Credit Account B
```

Both operations should succeed together.

If one succeeds and the other fails, the database becomes incorrect.

---

# 3. Example: Bank Transfer

Suppose:

### Account A

```text
Balance = ₹10,000
```

### Account B

```text
Balance = ₹5,000
```

We want to transfer ₹2,000 from A to B.

Before:

```text
A = ₹10,000
B = ₹5,000
```

After:

```text
A = ₹8,000
B = ₹7,000
```

Total money before:

```text
₹10,000 + ₹5,000 = ₹15,000
```

Total money after:

```text
₹8,000 + ₹7,000 = ₹15,000
```

The total remains unchanged.

---

# 4. Transaction in SQL

Suppose we have:

```sql
CREATE TABLE Accounts (
    account_id INT PRIMARY KEY,
    account_holder VARCHAR(100),
    balance DECIMAL(10,2)
);
```

Data:

| account_id | account_holder | balance |
| ---------: | -------------- | ------: |
|        101 | Ravi           |   10000 |
|        102 | Priya          |    5000 |

Transfer ₹2,000 from Ravi to Priya:

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 2000
WHERE account_id = 101;

UPDATE Accounts
SET balance = balance + 2000
WHERE account_id = 102;

COMMIT;
```

Here:

```text
START TRANSACTION
        ↓
Debit Ravi
        ↓
Credit Priya
        ↓
COMMIT
```

If something goes wrong:

```sql
ROLLBACK;
```

# 6. A — Atomicity

## Definition

> **Atomicity means that a transaction is treated as a single indivisible unit: either all operations succeed or none of them are applied.**

In simple words:

> **All or Nothing**

---

# 7. Atomicity Example

Consider a bank transfer:

```text
Transaction
    |
    ├── Debit ₹2,000 from A
    |
    └── Credit ₹2,000 to B
```

Suppose the first operation succeeds:

```text
A → ₹8,000
```

But the server crashes before the second operation:

```text
B → ₹5,000
```

Without atomicity:

```text
A lost ₹2,000
B did not receive ₹2,000
```

The database is incorrect.

With atomicity, the entire transaction is rolled back:

```text
A → ₹10,000
B → ₹5,000
```

The database returns to its previous state.

---

# 8. Atomicity Using COMMIT and ROLLBACK

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 2000
WHERE account_id = 101;

UPDATE Accounts
SET balance = balance + 2000
WHERE account_id = 102;

COMMIT;
```

If something goes wrong:

```sql
ROLLBACK;
```

### COMMIT

Makes the transaction changes permanent.

### ROLLBACK

Undo changes made by the transaction.

---

# 9. Real-Life Example of Atomicity

Consider online shopping.

You place an order:

```text
1. Create order
2. Reduce product inventory
3. Record payment
4. Create order item
```

These operations belong to one logical transaction.

Suppose payment succeeds but inventory update fails.

The system should not leave the order in an inconsistent state.

Atomicity ensures:

```text
All operations succeed
        OR
All operations are rolled back
```

---

# 10. C — Consistency

## Definition

> **Consistency ensures that a transaction changes the database from one valid state to another valid state while preserving all defined rules and constraints.**

In simple words:

> **The database must always follow its rules.**

---

# 11. What Does "Consistent" Mean?

Suppose we have a rule:

```text
Account balance cannot be negative.
```

Before transaction:

```text
Account A = ₹5,000
```

Attempt:

```text
Withdraw ₹6,000
```

After the transaction:

```text
Account A = -₹1,000
```

This violates the database rule.

Therefore, the transaction should fail or be rejected.

---

# 12. Database Constraints Help Maintain Consistency

Examples of constraints:

### Primary Key

```sql
student_id INT PRIMARY KEY
```

Prevents duplicate primary key values.

---

### NOT NULL

```sql
student_name VARCHAR(100) NOT NULL
```

Prevents NULL values.

---

### UNIQUE

```sql
email VARCHAR(100) UNIQUE
```

Prevents duplicate email addresses.

---

### CHECK

```sql
marks INT CHECK (marks >= 0 AND marks <= 100)
```

Prevents invalid marks.

---

### FOREIGN KEY

```sql
FOREIGN KEY (department_id)
REFERENCES Departments(department_id)
```

Prevents invalid department references.

---

# 13. Consistency Example Using Students

Suppose:

```sql
CREATE TABLE Students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100),
    marks INT CHECK (marks BETWEEN 0 AND 100)
);
```

The following is valid:

```sql
INSERT INTO Students
VALUES (101, 'Ravi', 85);
```

But:

```sql
INSERT INTO Students
VALUES (102, 'Priya', 150);
```

is invalid because:

```text
150 > 100
```

The database rejects the operation.

This helps maintain consistency.

---

# 14. Atomicity vs Consistency

These two concepts are often confused.

### Atomicity

Asks:

> Did the entire transaction happen or not?

### Consistency

Asks:

> Did the transaction preserve all database rules?

Example:

```text
Atomicity → All or Nothing
Consistency → Valid State → Valid State
```

---

# 15. I — Isolation

## Definition

> **Isolation ensures that concurrent transactions do not improperly interfere with each other.**

In simple words:

> **One transaction should not see or incorrectly affect the intermediate state of another transaction.**

This becomes important when many users access the database at the same time.

---

# 16. Why Do We Need Isolation?

Imagine two users:

```text
User A
User B
```

Both are trying to purchase the last available product.

Initial stock:

```text
Stock = 1
```

User A checks:

```text
Stock = 1
```

At almost the same time, User B checks:

```text
Stock = 1
```

Both think the product is available.

Without proper isolation:

```text
User A → purchases product
User B → purchases product
```

Now:

```text
Stock = -1
```

This is incorrect.

Isolation mechanisms prevent such problems.

---

# 17. Concurrent Transactions

Suppose:

```text
Transaction T1
Transaction T2
```

are executing at the same time.

Without proper isolation:

```text
T1 ──────────────
       ↘
        Conflict
       ↗
T2 ──────────────
```

With proper isolation:

```text
T1 ──────────────

T2 ──────────────

Database ensures controlled interaction.
```

---

# 18. Common Isolation Problems

Poor isolation can lead to:

1. Dirty Read
2. Non-Repeatable Read
3. Phantom Read
4. Lost Update

These are important DBMS concepts.

---

# 19. Dirty Read

A **dirty read** occurs when one transaction reads data that another transaction has modified but not yet committed.

Example:

Initial balance:

```text
₹10,000
```

Transaction T1:

```text
UPDATE balance
SET balance = 8000;
```

T1 has not committed.

Transaction T2 reads:

```text
₹8,000
```

Then T1 performs:

```text
ROLLBACK;
```

Actual balance becomes:

```text
₹10,000
```

But T2 had already seen:

```text
₹8,000
```

That is a **dirty read**.

---

# 20. Non-Repeatable Read

A non-repeatable read occurs when the same transaction reads the same row twice and gets different values because another transaction modified the row between the reads.

Example:

T1:

```text
First read → ₹10,000
```

T2:

```text
UPDATE balance → ₹8,000
COMMIT
```

T1:

```text
Second read → ₹8,000
```

T1 read two different values for the same row.

This is a **non-repeatable read**.

---

# 21. Phantom Read

A phantom read occurs when the same query returns a different set of rows because another transaction inserted or deleted rows.

Example:

T1:

```sql
SELECT *
FROM Students
WHERE marks > 80;
```

Suppose it returns:

```text
Ravi
Priya
```

T2 inserts:

```text
Arun → 90
```

and commits.

T1 runs the same query again:

```sql
SELECT *
FROM Students
WHERE marks > 80;
```

Now:

```text
Ravi
Priya
Arun
```

A new row appeared.

That new row is called a **phantom**.

---

# 22. Lost Update

A lost update occurs when two transactions read the same data and then update it, causing one update to overwrite another.

Example:

Initial balance:

```text
100
```

T1 reads:

```text
100
```

T2 reads:

```text
100
```

T1 changes:

```text
100 → 150
```

T2 changes:

```text
100 → 120
```

If T2 writes after T1:

```text
Final value = 120
```

T1's update to 150 is lost.

---

# 23. Isolation Levels

Most relational database systems provide different isolation levels.

The standard levels are:

```text
1. Read Uncommitted
2. Read Committed
3. Repeatable Read
4. Serializable
```

Some databases also support additional mechanisms such as snapshot-based isolation.

---

# 24. Read Uncommitted

This is the lowest isolation level.

A transaction may read uncommitted changes from another transaction.

Possible problem:

```text
Dirty Read
```

Conceptually:

```text
Performance → High
Consistency/Isolation → Low
```

---

# 25. Read Committed

A transaction can only read committed data.

This prevents:

```text
Dirty Reads
```

But depending on the database implementation, it may still allow:

```text
Non-Repeatable Reads
Phantom Reads
```

---

# 26. Repeatable Read

If a transaction reads a row, repeated reads of that row within the transaction are protected from certain concurrent modifications.

It prevents:

```text
Dirty Reads
Non-Repeatable Reads
```

Phantom behavior depends on the database's implementation and concurrency mechanism.

---

# 27. Serializable

This provides the strongest standard isolation level.

It aims to make concurrent transactions behave as though they were executed one after another.

```text
T1 → Complete
       ↓
T2 → Complete
```

instead of allowing conflicting operations to behave as if they were freely interleaved.

Advantages:

* Strong consistency
* Prevents major concurrency anomalies

Disadvantage:

* Lower concurrency
* Potentially more waiting/locking

---

# 28. Isolation Level Comparison

| Isolation Level  | Dirty Read | Non-Repeatable Read | Phantom Read       |
| ---------------- | ---------- | ------------------- | ------------------ |
| Read Uncommitted | Possible   | Possible            | Possible           |
| Read Committed   | Prevented  | Possible            | Possible           |
| Repeatable Read  | Prevented  | Prevented           | Database-dependent |
| Serializable     | Prevented  | Prevented           | Prevented          |

The exact behavior can vary with the database engine and its concurrency-control implementation.

---

# 29. D — Durability

## Definition

> **Durability means that once a transaction is successfully committed, its changes survive subsequent failures such as crashes or power loss.**

In simple words:

> **Once committed, the data stays saved.**

---

# 30. Durability Example

Suppose you transfer:

```text
₹2,000
```

from A to B.

The transaction completes:

```sql
COMMIT;
```

Then:

```text
Power failure
```

occurs.

After the database server restarts, the transfer should still be reflected.

The database should not return to the old state.

That is **durability**.

---

# 31. How Does Durability Work?

Database systems use mechanisms such as:

* Transaction logs
* Write-ahead logging (WAL)
* Recovery mechanisms
* Redundant storage
* Checkpoints
* Disk persistence

The exact implementation depends on the database system.

---

# 32. Transaction Log

A database maintains information about changes so it can recover after a failure.

Conceptually:

```text
Transaction Log

T1:
Debit Account A → ₹2,000
Credit Account B → ₹2,000
COMMIT
```

If the database crashes, the recovery system can use the log to determine what committed work must be preserved.

---

# 33. Write-Ahead Logging

A common recovery technique is **Write-Ahead Logging (WAL)**.

The basic idea is:

> The log record describing a change is persisted before the corresponding data change is considered safely persisted.

Conceptually:

```text
Transaction
     ↓
Write log
     ↓
Persist log
     ↓
Write/update data
     ↓
COMMIT
```

This allows the database to recover from failures.

---

# 34. ACID Example — Bank Transfer

Let's combine all four properties.

Suppose:

```text
Account A = ₹10,000
Account B = ₹5,000
```

Transfer:

```text
₹2,000
```

Transaction:

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 2000
WHERE account_id = 101;

UPDATE Accounts
SET balance = balance + 2000
WHERE account_id = 102;

COMMIT;
```

---

## Atomicity

Either:

```text
A - ₹2,000
B + ₹2,000
```

both happen,

or:

```text
Nothing happens.
```

---

## Consistency

The database rules remain valid.

For example:

```text
Balance cannot become invalid.
Foreign keys must remain valid.
Constraints must be satisfied.
```

---

## Isolation

Other transactions should not observe an invalid intermediate state such as:

```text
A = ₹8,000
B = ₹5,000
```

while the transfer is still incomplete.

---

## Durability

After:

```sql
COMMIT;
```

the transfer remains saved even if the server crashes immediately afterward.

# 37. ACID and COMMIT

`COMMIT` means:

> Make the transaction's changes permanent.

Example:

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;

COMMIT;
```

After successful commit:

```text
Changes → Permanent
```

---

# 38. ACID and ROLLBACK

`ROLLBACK` means:

> Undo the changes made by the current transaction that have not been committed.

Example:

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;

ROLLBACK;
```

The update is undone.

---

# 39. SAVEPOINT

A transaction can also create intermediate points using `SAVEPOINT`.

Example:

```sql
START TRANSACTION;

UPDATE Accounts
SET balance = balance - 1000
WHERE account_id = 101;

SAVEPOINT after_debit;

UPDATE Accounts
SET balance = balance + 1000
WHERE account_id = 102;

ROLLBACK TO after_debit;

COMMIT;
```

`ROLLBACK TO` a savepoint undoes changes after that savepoint without necessarily undoing the entire transaction.

# 42. ACID vs BASE

ACID is commonly associated with traditional transactional databases.

BASE is a different consistency approach commonly associated with some distributed systems.

### ACID

```text
Atomicity
Consistency
Isolation
Durability
```

Focus:

```text
Strong transactional correctness
```

### BASE

Often expanded as:

```text
Basically Available
Soft state
Eventual consistency
```

Focus:

```text
Availability and scalability
```

These are broad design philosophies, and real systems can combine different techniques.

---

# 43. ACID vs BASE

| ACID                                          | BASE                                               |
| --------------------------------------------- | -------------------------------------------------- |
| Strong transactional guarantees               | Often favors availability and eventual consistency |
| Common in traditional relational transactions | Common in some distributed systems                 |
| Strong consistency is emphasized              | Eventual consistency may be accepted               |
| Transactions are central                      | Distributed scalability is often emphasized        |
