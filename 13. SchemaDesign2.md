# Netflix Database Schema Design

## 1. What is Schema Design?

**Schema design** means deciding:

* What tables are needed
* What data each table stores
* Primary keys
* Foreign keys
* Relationships between tables

For a Netflix-like application, we need to store information about **users, profiles, movies/shows, genres, subscriptions, and watch history**.

---

# 2. Main Entities

A simple Netflix system can have these main entities:

1. Users
2. Profiles
3. Movies/Shows
4. Genres
5. Subscriptions
6. Watch History
7. Ratings

---

# 3. USERS Table

Stores information about the person who has a Netflix account.

### USERS

| Column     | Description           |
| ---------- | --------------------- |
| user_id    | Unique ID of user     |
| name       | User's name           |
| email      | Email address         |
| password   | Account password      |
| created_at | Account creation date |

**Primary Key:** `user_id`

Example:

| user_id | name  | email                                     |
| ------: | ----- | ----------------------------------------- |
|       1 | Ravi  | [ravi@gmail.com](mailto:ravi@gmail.com)   |
|       2 | Priya | [priya@gmail.com](mailto:priya@gmail.com) |

---

# 4. PROFILES Table

One Netflix account can have multiple profiles.

For example:

**Ravi's account**

* Ravi
* Mom
* Kids

### PROFILES

| Column       | Description       |
| ------------ | ----------------- |
| profile_id   | Unique profile ID |
| user_id      | Account owner     |
| profile_name | Name of profile   |
| age_group    | Adult/Kids        |

**Primary Key:** `profile_id`
**Foreign Key:** `user_id`

Relationship:

```text
USER
  |
  | 1 : M
  |
PROFILES
```

One user can have many profiles.

---

# 5. CONTENT Table

Netflix has different types of content such as:

* Movies
* TV Shows

We can keep both in one table to make our design simple.

### CONTENT

| Column       | Description       |
| ------------ | ----------------- |
| content_id   | Unique content ID |
| title        | Movie/show name   |
| content_type | Movie or TV Show  |
| release_year | Year released     |
| duration     | Duration          |
| description  | Short description |

**Primary Key:** `content_id`

Example:

| content_id | title           | content_type | release_year |
| ---------: | --------------- | ------------ | -----------: |
|        101 | RRR             | Movie        |         2022 |
|        102 | Stranger Things | TV Show      |         2016 |
|        103 | Leo             | Movie        |         2023 |

---

# 6. GENRES Table

Stores different genres.

Examples:

* Action
* Comedy
* Drama
* Horror
* Thriller

### GENRES

| Column     | Description     |
| ---------- | --------------- |
| genre_id   | Unique genre ID |
| genre_name | Genre name      |

**Primary Key:** `genre_id`

Example:

| genre_id | genre_name |
| -------: | ---------- |
|        1 | Action     |
|        2 | Comedy     |
|        3 | Drama      |

---

# 7. CONTENT_GENRES Table

A movie can belong to multiple genres.

For example:

**RRR → Action + Drama**

A genre can also contain many movies.

Therefore:

```text
CONTENT M : N GENRES
```

We need a **junction table** to solve this many-to-many relationship.

### CONTENT_GENRES

| Column     | Description |
| ---------- | ----------- |
| content_id | Content ID  |
| genre_id   | Genre ID    |

**Foreign Keys:**

* `content_id` → `CONTENT`
* `genre_id` → `GENRES`

Example:

| content_id | genre_id |
| ---------: | -------: |
|        101 |        1 |
|        101 |        3 |
|        102 |        3 |

Here:

```text
RRR → Action
RRR → Drama
```

---

# 8. SUBSCRIPTIONS Table

Stores the subscription information of users.

### SUBSCRIPTIONS

| Column          | Description                     |
| --------------- | ------------------------------- |
| subscription_id | Unique subscription ID          |
| user_id         | User who purchased subscription |
| plan_name       | Basic/Standard/Premium          |
| start_date      | Subscription start              |
| end_date        | Subscription end                |
| status          | Active/Expired                  |

**Primary Key:** `subscription_id`
**Foreign Key:** `user_id`

Relationship:

```text
USER 1 : M SUBSCRIPTIONS
```

A user may have different subscriptions over time.

---

# 9. WATCH_HISTORY Table

Stores what a profile has watched.

For example:

```text
Ravi → watched RRR
Priya → watched Leo
```

### WATCH_HISTORY

| Column     | Description          |
| ---------- | -------------------- |
| history_id | Unique history ID    |
| profile_id | Profile that watched |
| content_id | Content watched      |
| watched_at | Date/time watched    |
| progress   | Watching progress    |

**Primary Key:** `history_id`

**Foreign Keys:**

* `profile_id` → `PROFILES`
* `content_id` → `CONTENT`

Relationship:

```text
PROFILE 1 : M WATCH_HISTORY
CONTENT 1 : M WATCH_HISTORY
```

---

# 10. RATINGS Table

Users can rate content.

For example:

```text
Ravi → RRR → 5 stars
Priya → Leo → 4 stars
```

### RATINGS

| Column     | Description           |
| ---------- | --------------------- |
| rating_id  | Unique rating ID      |
| profile_id | Profile giving rating |
| content_id | Content being rated   |
| rating     | Rating value          |
| rated_at   | Date/time             |

**Primary Key:** `rating_id`

**Foreign Keys:**

* `profile_id` → `PROFILES`
* `content_id` → `CONTENT`

---

# 11. Complete Schema

The simplified Netflix database looks like this:

```text
                    USERS
                      |
                    1 : M
                      |
                   PROFILES
                    /    \
                 1:M      1:M
                  /          \
        WATCH_HISTORY       RATINGS
             |                 |
            M:1               M:1
             |                 |
          CONTENT <------------+
             |
            M:N
             |
       CONTENT_GENRES
             |
            M:1
             |
           GENRES


                    USERS
                      |
                    1 : M
                      |
                SUBSCRIPTIONS
```

---

# 12. Schema in Table Format

| Table          | Primary Key           | Important Foreign Key  |
| -------------- | --------------------- | ---------------------- |
| USERS          | user_id               | —                      |
| PROFILES       | profile_id            | user_id                |
| CONTENT        | content_id            | —                      |
| GENRES         | genre_id              | —                      |
| CONTENT_GENRES | content_id + genre_id | content_id, genre_id   |
| SUBSCRIPTIONS  | subscription_id       | user_id                |
| WATCH_HISTORY  | history_id            | profile_id, content_id |
| RATINGS        | rating_id             | profile_id, content_id |

---

# 13. Relationships

| Relationship            | Cardinality |
| ----------------------- | ----------- |
| User → Profiles         | 1 : M       |
| User → Subscriptions    | 1 : M       |
| Profile → Watch History | 1 : M       |
| Content → Watch History | 1 : M       |
| Profile → Ratings       | 1 : M       |
| Content → Ratings       | 1 : M       |
| Content → Genres        | M : N       |

---

# 14. Why Do We Need CONTENT_GENRES?

Suppose we directly store genres inside `CONTENT`:

```text
content_id | title | genres
101        | RRR   | Action, Drama
```

This is not a good relational design because multiple values are stored in one column.

Instead:

```text
CONTENT
101 | RRR
```

and:

```text
CONTENT_GENRES
101 | 1
101 | 3
```

So:

```text
RRR → Action
RRR → Drama
```

This is cleaner and easier to query.

# 15. Important Schema Design Rules

Remember these basic rules:

### Rule 1: Entity → Table

```text
User → USERS
Movie → CONTENT
Genre → GENRES
```

### Rule 2: Unique identifier → Primary Key

```text
user_id → PRIMARY KEY
content_id → PRIMARY KEY
```

### Rule 3: 1:M relationship → Foreign Key on the many side

```text
USER 1 : M PROFILE

PROFILES.user_id → USERS.user_id
```

### Rule 4: M:N relationship → Junction Table

```text
CONTENT M : N GENRES

        ↓

CONTENT_GENRES
```

# 16. Simple Schema Design Process

When designing a Netflix database:

```text
Requirements
     ↓
Identify Entities
     ↓
Create Tables
     ↓
Identify Attributes
     ↓
Choose Primary Keys
     ↓
Identify Relationships
     ↓
Add Foreign Keys
```

For example:

```text
Netflix Application
       ↓
User
Profile
Content
Genre
Subscription
Watch History
Rating
       ↓
Create Tables
       ↓
Connect Tables using PK & FK
```

# 17. Final Netflix Schema

```text
USERS
- user_id PK
- name
- email
- password
- created_at

        |
        | 1:M
        ↓

PROFILES
- profile_id PK
- user_id FK
- profile_name
- age_group


CONTENT
- content_id PK
- title
- content_type
- release_year
- duration
- description

        |
        | M:N
        ↓

CONTENT_GENRES
- content_id FK
- genre_id FK

        ↑
        |
GENRES
- genre_id PK
- genre_name


PROFILES ────< WATCH_HISTORY >──── CONTENT

PROFILES ────< RATINGS >────────── CONTENT

USERS ────< SUBSCRIPTIONS
```

### In simple words

The main idea is:

**User creates profiles → Profiles watch content → Content belongs to genres → Profiles can rate content → User has subscriptions.**

This is a good **beginner-to-intermediate schema design example** for understanding entities, primary keys, foreign keys, cardinality, and many-to-many relationships.
