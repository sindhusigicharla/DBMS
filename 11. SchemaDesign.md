# Schema Design in DBMS

## Restaurant Food Delivery Application

### 1. What is Schema Design?

**Schema design** is the process of deciding:

* What tables are needed
* What columns each table contains
* Primary keys
* Foreign keys
* Relationships between tables

> **Schema = Blueprint/Structure of the Database**

---

## 2. Example: Food Delivery Application

Imagine an application like Swiggy or Zomato.

A customer:

```text

   ↓

```

We need a database to store all this information.



# 11. Why Do We Need Order_Items?

Suppose order `5001` contains:

```text
Chicken Biryani × 2
Veg Biryani × 1
Coke × 2
```

We should **not** store all food names in one column:

```text
❌ food = "Chicken Biryani, Veg Biryani, Coke"
```

Instead, create `Order_Items`.

```text
ORDER_ITEMS
-------------------------
order_item_id      PK
order_id           FK
food_id            FK
quantity
unit_price
```

Example:

| order_item_id | order_id | food_id | quantity | unit_price |
| ------------: | -------: | ------: | -------: | ---------: |
|             1 |     5001 |     301 |        2 |        250 |
|             2 |     5001 |     302 |        1 |        180 |

# 12. Order and Food Relationship

An order can contain many food items.

```text
Order → Many Food Items
```

A food item can also appear in many orders.

```text
Food Item → Many Orders
```

Therefore:

```text
Order M : N Food_Item
```

This is a **Many-to-Many relationship**.

We solve it using `Order_Items`.

```text
Orders
   │
   │ 1:M
   ↓
Order_Items
   ↑
   │ M:1
   │
Food_Items
```

### Important Rule

> **M:N relationship → create a third/junction table.**

# 18. Important Relationships

| Relationship              | Cardinality |
| ------------------------- | ----------- |
| Customer → Address        | 1 : M       |
| Customer → Order          | 1 : M       |
| Restaurant → Food Item    | 1 : M       |
| Category → Food Item      | 1 : M       |
| Restaurant → Order        | 1 : M       |
| Order → Order Item        | 1 : M       |
| Food Item → Order Item    | 1 : M       |
| Order → Food Item         | M : N       |
| Order → Payment           | 1 : 1       |
| Order → Delivery          | 1 : 1       |
| Delivery Agent → Delivery | 1 : M       |

# 19. Important Schema Design Rules

### Rule 1 — Entity → Table

```text
Customer → Customers
Restaurant → Restaurants
Food → Food_Items
```

### Rule 2 — Unique identifier → Primary Key

```text
customer_id → PK
restaurant_id → PK
order_id → PK
```

### Rule 3 — 1:M → FK on the many side

Example:

```text
Customer 1:M Orders
```

So:

```text
Orders.customer_id → FK
```

### Rule 4 — M:N → Junction table

```text
Order M:N Food_Item
```

Therefore:

```text
Order_Items
```

### Rule 5 — Avoid unnecessary duplication

Instead of storing:

```text
Customer Name
Customer Phone
Restaurant Name
Food Name
```

in every order row, keep them in their respective tables and connect them using keys.

# 20. Schema Design Process

Remember this simple process:

```text
Requirements
     ↓
Identify Entities
     ↓
Identify Attributes
     ↓
Choose Primary Keys
     ↓
Identify Relationships
     ↓
Determine Cardinality
     ↓
Add Foreign Keys
     ↓
Create Tables
```

---

# 21. Schema vs Instance

### Schema

The structure of the database.

```text
CUSTOMERS(
    customer_id,
    customer_name,
    phone
)
```

### Instance

The actual data currently stored.

```text
101 | Ravi  | 9876543210
102 | Priya | 9876543211
```

### Remember

> **Schema = Structure**
> **Instance = Data**

# 22. Final Example

Suppose:

```text
Ravi
  ↓
Spice Hub
  ↓
Chicken Biryani × 2
  ↓
Order #5001
  ↓
UPI Payment
  ↓
Delivery Agent Kumar
```

The database represents this as:

```text
Customer
   ↓
Order
   ↓
Order_Item
   ↓
Food_Item
   ↓
Restaurant

Order → Payment

Order → Delivery → Delivery_Agent
```

This is the basic idea of **schema design**: breaking a real-world application into meaningful tables and connecting those tables using keys and relationships.
