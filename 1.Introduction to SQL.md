# Introduction to Databases

## What Is Data?

**Data** is a collection of raw facts or values that can be stored and processed.

Examples:

- Student name: `Asha`
- Age: `20`
- Date of birth: `2005-04-12`
- Product price: `499.00`

When data is organized and given meaning, it becomes **information**. For example, individual marks are data, while a student's calculated average is information.

## Why Not Store Everything in Excel or Other Software?

Excel and similar spreadsheet applications are useful for small, simple, and mostly individual tasks. However, they are not ideal for large or shared data systems because:

- Large files can become slow and difficult to manage.
- Multiple users may overwrite each other's changes.
- Repeated data can cause inconsistencies.
- Relationships between different types of data are difficult to enforce.
- Access control and security are limited compared with a database system.
- Validating data and maintaining rules becomes difficult.
- Backups, recovery, and reliable multi-step updates are harder to manage.

For example, a school may begin with an Excel sheet, but separate students, courses, enrollments, payments, and results are easier to manage in a database. A database is designed to store, organize, protect, and retrieve data reliably.

## Problems with Storing Data in Plain Files

Storing data in files such as CSV files may work for a small amount of data, but it creates serious problems as the system grows.

### 1. Inefficient Searching

To find a student's PSP in a large file, a program may need to open the file and check each row until it finds the student. If the file contains `N` rows, this may require **O(N)** work. Searching millions of records this way is slow and inefficient.

Databases use indexes and query-processing techniques to find data much faster.

## How Searching Happens in a Database

When a database receives a query, it does not always scan every row. The database first examines the query and chooses an execution plan. If a suitable index exists, it can use the index to locate the required rows and then read those rows from the table.

For example:

```sql
SELECT psp
FROM students
WHERE roll_number = 105;
```

If `roll_number` has an index, the database can search the index for `105` instead of checking every student one by one. It then follows the index reference to retrieve the matching row.

Without a suitable index, the database may perform a **full table scan**, in which it reads and checks each row. An index can make searches much faster, but indexes also require additional storage and can make insert and update operations slightly more expensive because the index must be maintained.

The exact search method depends on the database system, the index type, the query, and the data distribution. One of the most common index structures in relational databases is the **B+ tree**.

### Binary Trees

A **binary tree** is a tree data structure in which each node can have at most two children:

- A left child
- A right child

In a **binary search tree**, values smaller than a node are placed on the left and values larger than a node are placed on the right. This arrangement allows a search to eliminate part of the tree at each step.

For a balanced binary search tree, searching can take approximately **O(log N)** time. However, if values are inserted in an unfavorable order, the tree can become unbalanced and behave like a linked list, making searching **O(N)**.

Binary trees are useful for understanding tree-based searching, but they are not usually the best structure for indexes on large tables stored on disk. A binary tree may require many levels and therefore many disk accesses.

### B+ Trees

A **B+ tree** is a balanced, multi-level tree designed to work efficiently with storage systems such as hard disks and SSDs.

Important features of a B+ tree include:

- Each internal node can have many children, not just two.
- The tree remains balanced as values are inserted and deleted.
- Internal nodes store keys used for navigation.
- The actual indexed values or row references are stored in the leaf nodes.
- Leaf nodes are linked in sorted order, making range searches efficient.

For example, a query such as:

```sql
SELECT *
FROM students
WHERE roll_number BETWEEN 100 AND 120;
```

can find the first matching value in the B+ tree and then move through linked leaf nodes to find the remaining values in order.

### Binary Tree and B+ Tree Comparison

| Binary Search Tree | B+ Tree |
|---|---|
| Each node has at most two children | Each node can have many children |
| May become unbalanced | Remains balanced |
| Can require many levels for large data | Has fewer levels for large data |
| Mainly suitable for memory-based structures | Designed to reduce disk or storage access |
| Range searches are less efficient | Linked leaves make range searches efficient |

### 2. Data Integrity

Plain files usually do not enforce data types or business rules. For example, a `psp` value might accidentally be stored as `Hello` instead of a number:

```text
Rahul,1,Hello,100,0,1
```

There may be no automatic validation to prevent this invalid value. A database can enforce data types, required fields, uniqueness, and other rules to maintain **data integrity**.

### 3. Concurrency

Multiple users or applications may read or update the same data at the same time. If two users update the same file, one update may overwrite the other, or the file may become inconsistent.

A database manages concurrent access and uses transactions to ensure that updates are handled safely and reliably.

### 4. Security

File-based storage usually provides limited user-level access control. Anyone who can open a file may be able to read or modify all of its contents. For example, storing user passwords in a plain file could expose them to unauthorized users.

A database can authenticate users and assign permissions, such as allowing one user to read data while allowing another user to update it. Passwords should also be stored using secure password-hashing methods rather than as plain text.

## What Is an RDBMS?

**RDBMS** stands for **Relational Database Management System**. It is software that stores data in related tables.

An RDBMS organizes data using:

- **Tables:** Store a particular type of data.
- **Rows:** Represent individual records.
- **Columns:** Represent properties of records.
- **Keys:** Identify records and connect related tables.

For example, a college database may contain:

- `students(student_id, name)`
- `courses(course_id, course_name)`
- `enrollments(student_id, course_id)`

The `enrollments` table connects students with courses through their IDs.

Examples of RDBMS software include MySQL, PostgreSQL, Oracle Database, Microsoft SQL Server, and SQLite. RDBMSs commonly use **SQL (Structured Query Language)** to create, retrieve, update, and delete data.

## What Is NoSQL or Non-Relational DBMS?

**NoSQL** means **Not Only SQL**. A NoSQL or non-relational DBMS stores data without requiring the traditional table-and-relationship structure used by an RDBMS.

NoSQL databases may store data as:

- Documents
- Key-value pairs
- Graphs
- Wide-column records

They are useful when data changes frequently, has a flexible structure, or must be distributed across many servers. Examples include MongoDB, Redis, Cassandra, and Neo4j.

### RDBMS and NoSQL Comparison

| RDBMS | NoSQL |
|---|---|
| Stores data mainly in related tables | Uses documents, key-value pairs, graphs, or other models |
| Usually has a fixed, predefined schema | Usually supports a flexible schema |
| Uses relationships and joins | Often stores related data together or handles relationships differently |
| Strong support for SQL and transactions | Designed for flexible and highly scalable applications |
| Suitable for structured business data | Suitable for flexible, rapidly changing, or very large distributed data |

Neither type is always better. The choice depends on the data and application requirements.

## Properties of a Relational Database

### 1. Data Is Represented as Tables

A relational database represents data as a collection of tables. Each table stores information about an entity or a relationship between entities.

For example:

- A `students` table stores information about students.
- A `student_batches` table stores which student belongs to which batch. This represents a relationship between students and batches.

### 2. Every Row Should Be Uniquely Identifiable

In the relational model, two rows should not represent exactly the same record. A **primary key**, such as `roll_number` or `student_id`, is normally used to distinguish rows.

For example, two students may have the same name, attendance, and PSP, but their roll numbers can be different. In standard SQL, duplicate rows are technically possible unless a primary key or another uniqueness constraint prevents them, so important tables should define an appropriate key.

### 3. Values in a Column Have the Same Data Type

Values in one column follow the data type defined for that column.

For example:

- `name` can contain string values.
- `attendance` can contain integer or decimal values.
- `psp` can contain decimal values.

A value in the `psp` column should not be stored as an unrelated string.

### 4. Values Are Atomic

**Atomic** means indivisible. Each field should contain one value rather than a list or collection of values.

For example, multiple phone numbers should not be stored as a list in one `phone_numbers` column. They should be stored using a separate related table, which is covered during schema design.

Some SQL databases support lists or arrays in a column, but this is not part of the core SQL standard and can make querying more difficult.

### 5. Column Order Is Not Guaranteed

SQL does not guarantee that columns will be returned or handled in the order in which they were defined. Therefore, queries should explicitly use column names instead of relying on their position.

For example, prefer:

```sql
SELECT name, attendance, psp
FROM students;
```

Do not assume that `SELECT *` will always return columns in a particular order. Although MySQL commonly returns columns in their creation order, this should not be treated as a general SQL guarantee.

### 6. Row Order Is Not Guaranteed

SQL does not guarantee the order in which rows are returned. The result order may change between executions of the same query.

Use `ORDER BY` whenever a particular order is required:

```sql
SELECT *
FROM students
ORDER BY roll_number;
```

Do not rely on rows being returned in primary-key order or insertion order unless an `ORDER BY` clause explicitly specifies it.

### 7. Every Column Name Is Unique Within a Table

Each column in a table must have a unique name. A table cannot have two columns both named `name`, because a query such as `SELECT name FROM students` would be ambiguous.
