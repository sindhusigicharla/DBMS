# Normalization in DBMS

## 1. What is Normalization?

**Normalization** is a systematic process of organizing data in a database to:

* Reduce **data redundancy** (duplicate data)
* Avoid **data inconsistency**
* Prevent **insert, update, and delete anomalies**
* Improve **data integrity**
* Organize data into logically related tables
* Establish proper relationships between tables

### Simple Definition

> **Normalization is the process of decomposing a large table into smaller, well-structured tables while maintaining the relationships between the data.**

---

# 2. Why Do We Need Normalization?

Consider the following table:

### Student Table

| Student_ID | Student_Name | Course_ID | Course_Name | Instructor |
| ---------- | ------------ | --------- | ----------- | ---------- |
| 101        | Ravi         | C01       | Java        | Kumar      |
| 102        | Priya        | C01       | Java        | Kumar      |
| 103        | Arun         | C02       | Python      | Suresh     |
| 104        | Lakshmi      | C01       | Java        | Kumar      |

Notice that:

```text
Java → Kumar
```

is stored multiple times.

If 1,000 students are studying Java, we may store:

```text
Java → Kumar
```

1,000 times.

This creates **redundancy**.

---

# 3. Problems Caused by Redundancy

Data redundancy can cause three major types of anomalies:

1. **Insertion Anomaly**
2. **Update Anomaly**
3. **Deletion Anomaly**

These are extremely important for exams and interviews.

---

# 4. Insertion Anomaly

An **insertion anomaly** occurs when we cannot insert certain information into the database without inserting some unrelated information.

Consider:

| Student_ID | Student_Name | Course_ID | Course_Name |
| ---------- | ------------ | --------- | ----------- |
| 101        | Ravi         | C01       | Java        |
| 102        | Priya        | C02       | Python      |

Suppose a new course is introduced:

```text
C03 → SQL
```

But no student has enrolled yet.

Can we insert the course?

If `Student_ID` is mandatory, we cannot easily insert:

```text
C03 | SQL
```

because the table is designed around students.

We would have to insert a fake student or leave student information NULL.

This is an **insertion anomaly**.

### Solution

Separate the tables:

### Student

| Student_ID | Student_Name |
| ---------- | ------------ |
| 101        | Ravi         |
| 102        | Priya        |

### Course

| Course_ID | Course_Name |
| --------- | ----------- |
| C01       | Java        |
| C02       | Python      |
| C03       | SQL         |

Now we can add a course without requiring a student.

---

# 5. Update Anomaly

An **update anomaly** occurs when the same piece of information is stored in multiple places and we need to update all occurrences.

Consider:

| Student_ID | Student_Name | Course_ID | Course_Name | Instructor |
| ---------- | ------------ | --------- | ----------- | ---------- |
| 101        | Ravi         | C01       | Java        | Kumar      |
| 102        | Priya        | C01       | Java        | Kumar      |
| 103        | Arun         | C01       | Java        | Kumar      |

Suppose instructor Kumar is replaced by:

```text
Ramesh
```

We need to update three rows.

If we update only two rows:

| Student_ID | Course_ID | Course_Name | Instructor |
| ---------- | --------- | ----------- | ---------- |
| 101        | C01       | Java        | Ramesh     |
| 102        | C01       | Java        | Ramesh     |
| 103        | C01       | Java        | Kumar      |

The database becomes inconsistent.

This is an **update anomaly**.

### Solution

Store course information separately.

### Course

| Course_ID | Course_Name | Instructor |
| --------- | ----------- | ---------- |
| C01       | Java        | Kumar      |

Now we only update one row.

---

# 6. Deletion Anomaly

A **deletion anomaly** occurs when deleting one piece of information accidentally removes another important piece of information.

Consider:

| Student_ID | Student_Name | Course_ID | Course_Name |
| ---------- | ------------ | --------- | ----------- |
| 101        | Ravi         | C01       | Java        |
| 102        | Priya        | C01       | Java        |
| 103        | Arun         | C02       | Python      |

Suppose Arun is the only student enrolled in Python.

If Arun's record is deleted:

```sql
DELETE FROM Student
WHERE Student_ID = 103;
```

we also lose:

```text
C02 → Python
```

information.

The course still exists, but the database no longer stores it.

This is a **deletion anomaly**.

### Solution

Store students and courses separately.

---

# 7. Main Goal of Normalization

Normalization tries to achieve:

```text
Less redundancy
       ↓
Fewer anomalies
       ↓
Better data integrity
       ↓
Better database design
```

---

# 8. Important Concepts Before Normalization

To understand normalization, we need to understand:

* Attribute
* Tuple
* Relation
* Primary Key
* Candidate Key
* Super Key
* Functional Dependency

---

# 9. Attribute

An **attribute** is a column of a table.

Example:

```text
Student
```

| Student_ID | Name | Age | Department |
| ---------- | ---- | --- | ---------- |
| 101        | Ravi | 21  | CSE        |

Attributes are:

```text
Student_ID
Name
Age
Department
```

---

# 10. Tuple

A **tuple** is a row in a relational table.

Example:

| Student_ID | Name | Age |
| ---------- | ---- | --- |
| 101        | Ravi | 21  |

The complete row:

```text
101 | Ravi | 21
```

is a tuple.

---

# 11. Primary Key

A **primary key** uniquely identifies each row.

Example:

```text
Student_ID
```

| Student_ID | Name  |
| ---------- | ----- |
| 101        | Ravi  |
| 102        | Priya |
| 103        | Arun  |

Here:

```text
Student_ID → Name
```

because knowing Student_ID allows us to determine the student's name.

---

# 12. Candidate Key

A **candidate key** is a minimal super key.

Suppose:

| Student_ID | Email                                     | Name  |
| ---------- | ----------------------------------------- | ----- |
| 101        | [ravi@gmail.com](mailto:ravi@gmail.com)   | Ravi  |
| 102        | [priya@gmail.com](mailto:priya@gmail.com) | Priya |

Both:

```text
Student_ID
Email
```

can uniquely identify a student.

Therefore:

```text
Candidate Keys = {Student_ID, Email}
```

One candidate key is selected as the **primary key**.

---

# 13. Super Key

A **super key** is any set of attributes that uniquely identifies a row.

Suppose:

```text
Student_ID
Email
Name
```

Student_ID alone uniquely identifies the student.

Therefore:

```text
Student_ID
```

is a super key.

These can also be super keys:

```text
(Student_ID, Name)
(Student_ID, Email)
(Student_ID, Name, Email)
```

But they are not necessarily candidate keys because they contain unnecessary attributes.

---

# 14. Functional Dependency

Functional dependency is one of the most important concepts in normalization.

It is represented as:

```text
A → B
```

Read as:

> A determines B.

Example:

```text
Student_ID → Student_Name
```

If we know Student_ID, we can determine Student_Name.

Example:

```text
101 → Ravi
102 → Priya
103 → Arun
```

---

# 15. Example of Functional Dependency

Consider:

| Student_ID | Student_Name | Department |
| ---------- | ------------ | ---------- |
| 101        | Ravi         | CSE        |
| 102        | Priya        | ECE        |
| 103        | Arun         | CSE        |

We can say:

```text
Student_ID → Student_Name
Student_ID → Department
```

But we cannot generally say:

```text
Department → Student_Name
```

because:

```text
CSE → Ravi
CSE → Arun
```

There are multiple students in CSE.

---

# 16. Types of Functional Dependencies

Important types include:

1. Trivial Functional Dependency
2. Non-Trivial Functional Dependency
3. Full Functional Dependency
4. Partial Dependency
5. Transitive Dependency

The last three are especially important for normalization.

---

# 17. Trivial Functional Dependency

A functional dependency is trivial if the right side is already part of the left side.

Example:

```text
(Student_ID, Name) → Name
```

Since `Name` is already included in the left-hand side, this is trivial.

---

# 18. Non-Trivial Functional Dependency

Example:

```text
Student_ID → Name
```

Here:

```text
Name
```

is not part of:

```text
Student_ID
```

Therefore it is a non-trivial functional dependency.

---

# 19. First Normal Form — 1NF

A table is in **First Normal Form (1NF)** if:

* Each column contains atomic values.
* There are no repeating groups.
* Each cell contains a single value.

### Example — Not in 1NF

| Student_ID | Name  | Phone      |
| ---------- | ----- | ---------- |
| 101        | Ravi  | 9876, 8765 |
| 102        | Priya | 7654       |

The `Phone` column contains multiple values.

This violates 1NF.

---

# 20. Converting to 1NF

Separate the phone numbers into individual rows:

| Student_ID | Name  | Phone |
| ---------- | ----- | ----- |
| 101        | Ravi  | 9876  |
| 101        | Ravi  | 8765  |
| 102        | Priya | 7654  |

Now every cell contains a single value.

Therefore the table satisfies the atomicity requirement of 1NF.

---

# 21. Another 1NF Example

### Not in 1NF

| Student_ID | Name  | Courses           |
| ---------- | ----- | ----------------- |
| 101        | Ravi  | Java, Python, SQL |
| 102        | Priya | Java, HTML        |

The `Courses` column contains multiple values.

### In 1NF

| Student_ID | Name  | Course |
| ---------- | ----- | ------ |
| 101        | Ravi  | Java   |
| 101        | Ravi  | Python |
| 101        | Ravi  | SQL    |
| 102        | Priya | Java   |
| 102        | Priya | HTML   |

---

# 22. Important Point About 1NF

1NF does **not** mean:

> "There can be no duplicate values."

It means:

> **Each attribute value must be atomic and indivisible according to the chosen relational model.**

For example:

| Student_ID | Name |
| ---------- | ---- |
| 101        | Ravi |
| 102        | Ravi |

This is allowed in 1NF.

Names do not have to be unique.

---

# 23. Second Normal Form — 2NF

A table is in **2NF** if:

1. It is already in **1NF**
2. It has **no partial dependency**

Partial dependency is mainly relevant when the table has a **composite candidate key**.

---

# 24. What is a Composite Key?

A composite key consists of two or more attributes.

Example:

```text
(Student_ID, Course_ID)
```

Suppose:

| Student_ID | Course_ID | Student_Name | Course_Name | Marks |
| ---------- | --------- | ------------ | ----------- | ----- |
| 101        | C01       | Ravi         | Java        | 85    |
| 101        | C02       | Ravi         | Python      | 90    |
| 102        | C01       | Priya        | Java        | 80    |

Here:

```text
(Student_ID, Course_ID)
```

can uniquely identify a student's enrollment.

---

# 25. What is Partial Dependency?

Partial dependency occurs when a non-key attribute depends on only **part of a composite key**.

Consider:

```text
(Student_ID, Course_ID) → Marks
```

Marks depends on both:

```text
Student_ID + Course_ID
```

Therefore this is a full dependency.

But:

```text
Student_ID → Student_Name
```

Student_Name depends only on:

```text
Student_ID
```

not the entire composite key.

Therefore:

```text
Student_ID → Student_Name
```

is a **partial dependency**.

Similarly:

```text
Course_ID → Course_Name
```

is also a partial dependency.

---

# 26. Example of a Table Not in 2NF

| Student_ID | Course_ID | Student_Name | Course_Name | Marks |
| ---------- | --------- | ------------ | ----------- | ----- |
| 101        | C01       | Ravi         | Java        | 85    |
| 101        | C02       | Ravi         | Python      | 90    |
| 102        | C01       | Priya        | Java        | 80    |

Primary key:

```text
(Student_ID, Course_ID)
```

Functional dependencies:

```text
Student_ID → Student_Name
Course_ID → Course_Name
(Student_ID, Course_ID) → Marks
```

The first two are partial dependencies.

Therefore:

```text
Table is NOT in 2NF.
```

---

# 27. Converting the Table to 2NF

Split the table into three tables.

### Student

| Student_ID | Student_Name |
| ---------- | ------------ |
| 101        | Ravi         |
| 102        | Priya        |

### Course

| Course_ID | Course_Name |
| --------- | ----------- |
| C01       | Java        |
| C02       | Python      |

### Enrollment

| Student_ID | Course_ID | Marks |
| ---------- | --------- | ----- |
| 101        | C01       | 85    |
| 101        | C02       | 90    |
| 102        | C01       | 80    |

Now:

```text
Student_ID → Student_Name
Course_ID → Course_Name
(Student_ID, Course_ID) → Marks
```

There are no partial dependencies.

Therefore the design is in **2NF**.

---

# 28. Important 2NF Point

If a table has a **single-attribute primary key**, partial dependency cannot exist.

For example:

```text
Student_ID → Student_Name
```

If Student_ID is the entire key, there is no "part of the key."

Therefore:

> A table with a single-attribute key that is in 1NF is automatically in 2NF.

---

# 29. Third Normal Form — 3NF

A table is in **3NF** if:

1. It is already in **2NF**
2. It has no **transitive dependency** of non-key attributes on a key.

---

# 30. What is Transitive Dependency?

Consider:

```text
A → B
B → C
```

Therefore:

```text
A → C
```

This is a transitive dependency.

---

# 31. 3NF Example

Consider:

| Student_ID | Student_Name | Dept_ID | Dept_Name |
| ---------- | ------------ | ------- | --------- |
| 101        | Ravi         | D01     | CSE       |
| 102        | Priya        | D02     | ECE       |
| 103        | Arun         | D01     | CSE       |

Primary key:

```text
Student_ID
```

Functional dependencies:

```text
Student_ID → Student_Name
Student_ID → Dept_ID
Dept_ID → Dept_Name
```

Therefore:

```text
Student_ID → Dept_ID → Dept_Name
```

This is a transitive dependency.

So the table is **not in 3NF**.

---

# 32. Converting to 3NF

Create two tables.

### Student

| Student_ID | Student_Name | Dept_ID |
| ---------- | ------------ | ------- |
| 101        | Ravi         | D01     |
| 102        | Priya        | D02     |
| 103        | Arun         | D01     |

### Department

| Dept_ID | Dept_Name |
| ------- | --------- |
| D01     | CSE       |
| D02     | ECE       |

Now:

```text
Student_ID → Student_Name
Student_ID → Dept_ID

Dept_ID → Dept_Name
```

The transitive dependency has been removed from the Student table.

---

# 33. Another 3NF Example

Consider an employee table:

| Emp_ID | Emp_Name | Dept_ID | Dept_Name | Dept_Location |
| ------ | -------- | ------- | --------- | ------------- |
| E01    | Ravi     | D01     | IT        | Chennai       |
| E02    | Priya    | D02     | HR        | Hyderabad     |
| E03    | Arun     | D01     | IT        | Chennai       |

Dependencies:

```text
Emp_ID → Emp_Name
Emp_ID → Dept_ID
Dept_ID → Dept_Name
Dept_ID → Dept_Location
```

Therefore:

```text
Emp_ID → Dept_ID → Dept_Name
Emp_ID → Dept_ID → Dept_Location
```

This is transitive dependency.

### Decomposition

#### Employee

| Emp_ID | Emp_Name | Dept_ID |
| ------ | -------- | ------- |
| E01    | Ravi     | D01     |
| E02    | Priya    | D02     |
| E03    | Arun     | D01     |

#### Department

| Dept_ID | Dept_Name | Dept_Location |
| ------- | --------- | ------------- |
| D01     | IT        | Chennai       |
| D02     | HR        | Hyderabad     |

---

# 34. Summary of 1NF, 2NF and 3NF

| Normal Form | Main Requirement               |
| ----------- | ------------------------------ |
| 1NF         | Atomic values                  |
| 2NF         | 1NF + No partial dependency    |
| 3NF         | 2NF + No transitive dependency |

A simple way to remember:

```text
1NF → Atomic
2NF → No Partial Dependency
3NF → No Transitive Dependency
```

---

# 35. BCNF — Boyce-Codd Normal Form

**BCNF** is a stronger version of 3NF.

A relation is in BCNF if:

> For every non-trivial functional dependency X → Y, X must be a super key.

In simple words:

```text
Every determinant must be a candidate key/super key.
```

---

# 36. BCNF Example

Consider:

| Student | Course | Instructor |
| ------- | ------ | ---------- |
| Ravi    | DBMS   | Kumar      |
| Priya   | DBMS   | Kumar      |
| Ravi    | Java   | Suresh     |
| Arun    | Java   | Suresh     |

Suppose the rules are:

```text
(Student, Course) → Instructor
Instructor → Course
```

If an instructor teaches only one course:

```text
Kumar → DBMS
Suresh → Java
```

But:

```text
Instructor
```

is not a candidate key for the whole relation because multiple students can have the same instructor.

Therefore:

```text
Instructor → Course
```

violates BCNF.

---

# 37. BCNF Decomposition

Create:

### Instructor_Course

| Instructor | Course |
| ---------- | ------ |
| Kumar      | DBMS   |
| Suresh     | Java   |

### Student_Instructor

| Student | Instructor |
| ------- | ---------- |
| Ravi    | Kumar      |
| Priya   | Kumar      |
| Ravi    | Suresh     |
| Arun    | Suresh     |

Now the problematic dependency has been separated.

---

# 38. Difference Between 3NF and BCNF

### 3NF

For every functional dependency:

```text
X → A
```

at least one of the following should hold:

1. X is a super key

**OR**

2. A is a prime attribute.

### BCNF

For every functional dependency:

```text
X → A
```

X **must** be a super key.

Therefore:

```text
BCNF is stricter than 3NF.
```

---

# 39. Relationship Between Normal Forms

The general progression is:

```text
Unnormalized
      ↓
     1NF
      ↓
     2NF
      ↓
     3NF
      ↓
    BCNF
      ↓
     4NF
      ↓
     5NF
```

Each higher normal form generally imposes stronger constraints.

---

# 40. Fourth Normal Form — 4NF

4NF deals mainly with **multivalued dependencies**.

A table should be in:

```text
BCNF
```

and should not contain problematic **multivalued dependencies**.

---

# 41. Multivalued Dependency

A multivalued dependency occurs when one attribute determines multiple independent values of another attribute.

Consider:

| Student | Hobby   | Language |
| ------- | ------- | -------- |
| Ravi    | Cricket | English  |
| Ravi    | Cricket | Telugu   |
| Ravi    | Chess   | English  |
| Ravi    | Chess   | Telugu   |

Suppose Ravi has:

```text
Hobbies:
Cricket
Chess

Languages:
English
Telugu
```

Hobbies and languages are independent.

But because they are stored in one table, we need all combinations:

```text
Cricket + English
Cricket + Telugu
Chess + English
Chess + Telugu
```

This creates unnecessary combinations.

---

# 42. Converting to 4NF

Separate the independent multivalued attributes.

### Student_Hobby

| Student | Hobby   |
| ------- | ------- |
| Ravi    | Cricket |
| Ravi    | Chess   |

### Student_Language

| Student | Language |
| ------- | -------- |
| Ravi    | English  |
| Ravi    | Telugu   |

This removes the multivalued dependency problem.

---

# 43. Fifth Normal Form — 5NF

5NF is also called:

> **Project-Join Normal Form (PJ/NF)**

It deals with **join dependencies**.

5NF attempts to eliminate redundancy caused by complex relationships that can be reconstructed by joining multiple smaller relations.

It is less commonly required in everyday database design than 1NF, 2NF, 3NF, and BCNF.

---

# 44. Simple 5NF Example

Suppose we have:

```text
Supplier
Part
Project
```

A company may have relationships such as:

```text
Supplier supplies Part
Supplier works on Project
Part is used in Project
```

Sometimes storing all three relationships in one table creates unnecessary combinations.

We may decompose into:

```text
Supplier_Part
Supplier_Project
Part_Project
```

The original relationship can then be reconstructed using joins when the decomposition satisfies the required join dependency.

---

# 45. Normalization Example From Start to Finish

Let's take a larger example.

Suppose we have:

| Student_ID | Student_Name | Course_ID | Course_Name | Instructor_ID | Instructor_Name | Dept_ID | Dept_Name | Marks |
| ---------- | ------------ | --------- | ----------- | ------------- | --------------- | ------- | --------- | ----- |
| 101        | Ravi         | C01       | DBMS        | I01           | Kumar           | D01     | CSE       | 85    |
| 101        | Ravi         | C02       | Java        | I02           | Suresh          | D01     | CSE       | 90    |
| 102        | Priya        | C01       | DBMS        | I01           | Kumar           | D01     | CSE       | 80    |

This table contains a lot of repeated information.

---

# 46. Step 1 — Identify the Key

A student can enroll in multiple courses.

Therefore:

```text
(Student_ID, Course_ID)
```

can identify an enrollment.

So the composite key is:

```text
(Student_ID, Course_ID)
```

---

# 47. Step 2 — Identify Functional Dependencies

We can identify:

```text
Student_ID → Student_Name
```

```text
Course_ID → Course_Name
Course_ID → Instructor_ID
```

```text
Instructor_ID → Instructor_Name
Instructor_ID → Dept_ID
```

```text
Dept_ID → Dept_Name
```

And:

```text
(Student_ID, Course_ID) → Marks
```

---

# 48. Step 3 — Convert to 1NF

Assume all values are already atomic.

Therefore:

```text
Table is in 1NF.
```

---

# 49. Step 4 — Convert to 2NF

We have partial dependencies:

```text
Student_ID → Student_Name
```

and:

```text
Course_ID → Course_Name
```

because the key is:

```text
(Student_ID, Course_ID)
```

Decompose.

### Student

```text
Student_ID
Student_Name
```

### Course

```text
Course_ID
Course_Name
Instructor_ID
```

### Enrollment

```text
Student_ID
Course_ID
Marks
```

---

# 50. Step 5 — Convert to 3NF

Look at Course:

```text
Course_ID → Instructor_ID
Instructor_ID → Instructor_Name
Instructor_ID → Dept_ID
Dept_ID → Dept_Name
```

There are transitive dependencies.

Therefore split further.

### Student

| Student_ID | Student_Name |
| ---------- | ------------ |
| 101        | Ravi         |
| 102        | Priya        |

### Course

| Course_ID | Course_Name | Instructor_ID |
| --------- | ----------- | ------------- |
| C01       | DBMS        | I01           |
| C02       | Java        | I02           |

### Instructor

| Instructor_ID | Instructor_Name | Dept_ID |
| ------------- | --------------- | ------- |
| I01           | Kumar           | D01     |
| I02           | Suresh          | D01     |

### Department

| Dept_ID | Dept_Name |
| ------- | --------- |
| D01     | CSE       |

### Enrollment

| Student_ID | Course_ID | Marks |
| ---------- | --------- | ----- |
| 101        | C01       | 85    |
| 101        | C02       | 90    |
| 102        | C01       | 80    |

Now the data is much more organized.

---

# 51. Primary Keys and Foreign Keys After Normalization

After decomposition:

### Student

```text
Student_ID → Primary Key
```

### Course

```text
Course_ID → Primary Key
Instructor_ID → Foreign Key
```

### Instructor

```text
Instructor_ID → Primary Key
Dept_ID → Foreign Key
```

### Department

```text
Dept_ID → Primary Key
```

### Enrollment

```text
(Student_ID, Course_ID) → Composite Primary Key
Student_ID → Foreign Key
Course_ID → Foreign Key
```

---

# 52. SQL Representation

### Student

```sql
CREATE TABLE Student (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100)
);
```

### Department

```sql
CREATE TABLE Department (
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(100)
);
```

### Instructor

```sql
CREATE TABLE Instructor (
    instructor_id INT PRIMARY KEY,
    instructor_name VARCHAR(100),
    dept_id INT,
    FOREIGN KEY (dept_id)
        REFERENCES Department(dept_id)
);
```

### Course

```sql
CREATE TABLE Course (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(100),
    instructor_id INT,
    FOREIGN KEY (instructor_id)
        REFERENCES Instructor(instructor_id)
);
```

### Enrollment

```sql
CREATE TABLE Enrollment (
    student_id INT,
    course_id INT,
    marks INT,

    PRIMARY KEY (student_id, course_id),

    FOREIGN KEY (student_id)
        REFERENCES Student(student_id),

    FOREIGN KEY (course_id)
        REFERENCES Course(course_id)
);
```

---

# 53. Why Foreign Keys Are Important After Normalization

Normalization splits information into multiple tables.

For example:

```text
Student
   |
   | student_id
   ↓
Enrollment
   |
   | course_id
   ↓
Course
   |
   | instructor_id
   ↓
Instructor
   |
   | dept_id
   ↓
Department
```

Foreign keys maintain the relationships between these tables.

---

# 54. Normalization and Joins

After normalization, information is distributed across multiple tables.

Therefore, we use **JOINs** to retrieve combined information.

Example:

```sql
SELECT
    s.student_name,
    c.course_name,
    e.marks
FROM Student s
JOIN Enrollment e
    ON s.student_id = e.student_id
JOIN Course c
    ON e.course_id = c.course_id;
```

Result:

| student_name | course_name | marks |
| ------------ | ----------- | ----- |
| Ravi         | DBMS        | 85    |
| Ravi         | Java        | 90    |
| Priya        | DBMS        | 80    |

# 55. Normalization vs Denormalization

## Normalization

Data is split into multiple related tables.

Advantages:

* Less redundancy
* Better consistency
* Easier updates
* Better data integrity
* Fewer anomalies

Disadvantages:

* More tables
* More JOINs
* Complex queries can sometimes be slower

---

## Denormalization

Denormalization intentionally introduces some redundancy to improve read performance or simplify queries.

Example:

Instead of joining:

```text
Student
Enrollment
Course
```

we might store:

```text
Student_ID
Student_Name
Course_ID
Course_Name
Marks
```

in one table.

This may improve some read-heavy workloads but increases redundancy.

---

# 56. When Should We Normalize?

Normalization is particularly useful when:

* Designing transactional databases
* Storing frequently updated data
* Maintaining data consistency
* Avoiding duplicate information
* Designing OLTP systems

Examples:

```text
Banking systems
Student management systems
Hospital systems
Employee systems
E-commerce transaction systems
```

---

# 57. When Might We Denormalize?

Denormalization can be useful when:

* Read performance is very important
* Queries require many expensive joins
* Data is mostly read and rarely updated
* Reporting/analytics workloads need simplified access

For example:

```text
Data warehouse
Reporting systems
Analytics systems
```

But denormalization should be intentional.

# 59. Easy Way to Remember Normal Forms

Remember this sequence:

```text
1NF → Atomic Values
        ↓
2NF → Remove Partial Dependency
        ↓
3NF → Remove Transitive Dependency
        ↓
BCNF → Every Determinant is a Super Key
        ↓
4NF → Remove Multivalued Dependency
        ↓
5NF → Remove Join Dependency
```

# 60. Important Interview Question

### Q: Is every 3NF table in BCNF?

**No.**

BCNF is stricter than 3NF.

Therefore:

```text
BCNF ⊂ 3NF
```

More accurately, every BCNF relation satisfies 3NF, but some 3NF relations do not satisfy BCNF.

---

# 61. Important Interview Question

### Q: Can a table be in 1NF but not 2NF?

**Yes.**

Example:

```text
(Student_ID, Course_ID) → Marks
Student_ID → Student_Name
```

The table can satisfy atomicity but still have a partial dependency.

Therefore:

```text
1NF ≠ 2NF
```

---

# 62. Important Interview Question

### Q: Can a table be in 2NF but not 3NF?

**Yes.**

Example:

```text
Student_ID → Dept_ID
Dept_ID → Dept_Name
```

There is no partial dependency, but there is a transitive dependency.

Therefore:

```text
2NF ≠ 3NF
```

---

# 63. Important Interview Question

### Q: If a table has a single-column primary key, can it have partial dependency?

**No.**

Partial dependency requires a composite key.

For example:

```text
Student_ID → Student_Name
```

Student_ID is the complete key.

There is no smaller part of the key.

# 64. Practical Student-Course Example

Suppose you create this table:

```text
Student_Course
```

| Student_ID | Student_Name | Course_ID | Course_Name | Instructor | Marks |
| ---------- | ------------ | --------- | ----------- | ---------- | ----- |
| 1          | Ravi         | 101       | SQL         | Kumar      | 85    |
| 1          | Ravi         | 102       | Java        | Suresh     | 90    |
| 2          | Priya        | 101       | SQL         | Kumar      | 80    |

Primary key:

```text
(Student_ID, Course_ID)
```

Dependencies:

```text
Student_ID → Student_Name
```

```text
Course_ID → Course_Name
Course_ID → Instructor
```

```text
(Student_ID, Course_ID) → Marks
```

This is not in 2NF.

Decompose into:

```text
Student
---------
Student_ID
Student_Name

Course
---------
Course_ID
Course_Name
Instructor

Enrollment
---------
Student_ID
Course_ID
Marks
```

This is a classic example of converting a table to 2NF.

# 65. Example of Transitive Dependency

Suppose:

```text
Student_ID → Department_ID
Department_ID → Department_Name
```

Therefore:

```text
Student_ID → Department_Name
```

This is transitive dependency.

Solution:

```text
Student
---------
Student_ID
Student_Name
Department_ID

Department
---------
Department_ID
Department_Name
```

Start with:

Ensure:

# 69. One-Line Definitions for Exams

### 1NF

> A relation is in 1NF if all attribute values are atomic and there are no repeating groups.

### 2NF

> A relation is in 2NF if it is in 1NF and has no partial dependency of a non-prime attribute on a candidate key.

### 3NF

> A relation is in 3NF if it is in 2NF and has no transitive dependency of a non-prime attribute on a candidate key.

### BCNF

> A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a super key.

### 4NF

> A relation is in 4NF if it is in BCNF and contains no non-trivial multivalued dependency unless the determinant is a super key.

### 5NF

> A relation is in 5NF if every non-trivial join dependency is implied by the candidate keys.
