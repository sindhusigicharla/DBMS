# 5. Constraints in MySQL

## Why Constraints Are Important

A **constraint** is a rule applied to a table or column to control the data that can be stored. Constraints help the database reject invalid data instead of depending only on application code.

Constraints protect:

- **Accuracy:** Values follow valid rules.
- **Consistency:** Related tables do not contradict each other.
- **Uniqueness:** Duplicate identifiers are prevented.
- **Completeness:** Required values are present.
- **Relationships:** Child rows refer to valid parent rows.
- **Business rules:** Data follows conditions required by the organization.

This chapter covers:

- `NOT NULL`
- `UNIQUE`
- `PRIMARY KEY`
- `FOREIGN KEY`
- `DEFAULT`
- `CHECK`
- `AUTO_INCREMENT`
- Foreign key actions such as `ON DELETE CASCADE` and `ON UPDATE CASCADE`

---

## Learning Objectives

After completing this chapter, you should be able to:

- Explain the purpose of each MySQL constraint.
- Create tables using multiple constraints together.
- Add constraints to existing tables.
- Design practical relationships between departments, employees, students, products, and orders.
- Choose appropriate foreign-key actions.
- Avoid common errors involving `NULL`, duplicate values, and cascading deletes.

# 1. `NOT NULL`

The `NOT NULL` constraint requires a column to contain a value. It prevents the column from storing `NULL`.

## Syntax

```sql
column_name data_type NOT NULL
```

## Example

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100) NOT NULL,
    admission_date DATE NOT NULL
);
```

Every student must have a name and admission date.

This insert fails because `student_name` is missing:

```sql
INSERT INTO students (student_id, admission_date)
VALUES (1, '2026-09-09');
```

## `NULL` Is Not the Same as an Empty Value

These values have different meanings:

- `NULL`: The value is unknown, unavailable, or not provided.
- `''`: An empty string.
- `0`: The numeric value zero.
- `FALSE`: A false boolean value.

For example, an employee's middle name may legitimately be `NULL`, while an employee ID should normally never be `NULL`.

## Adding `NOT NULL` to an Existing Column

```sql
ALTER TABLE students
MODIFY COLUMN student_name VARCHAR(100) NOT NULL;
```

Before running this command, existing rows must not contain `NULL` in `student_name`.

## Removing `NOT NULL`

To allow `NULL`, modify the column without `NOT NULL`:

```sql
ALTER TABLE students
MODIFY COLUMN student_name VARCHAR(100) NULL;
```

## Best Practices

- Use `NOT NULL` for required values.
- Allow `NULL` only when the absence of a value has a clear meaning.
- Do not use empty strings as a replacement for every missing value.
- Check existing data before making a column required.

# 2. `UNIQUE`

The `UNIQUE` constraint prevents duplicate values in a column or combination of columns.

## Single-Column Unique Constraint

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_number VARCHAR(20) NOT NULL UNIQUE,
    email VARCHAR(254) NOT NULL UNIQUE,
    employee_name VARCHAR(100) NOT NULL
);
```

No two employees can have the same employee number or email address.

## Named Unique Constraint

Naming constraints makes them easier to identify and modify:

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_code VARCHAR(30) NOT NULL,
    product_name VARCHAR(150) NOT NULL,
    CONSTRAINT uq_products_code UNIQUE (product_code)
);
```

## Composite `UNIQUE` Constraint

A composite unique constraint prevents duplicate combinations of values:

```sql
CREATE TABLE product_prices (
    product_id INT NOT NULL,
    price_list_name VARCHAR(50) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    CONSTRAINT uq_product_price_list
        UNIQUE (product_id, price_list_name)
);
```

A product can appear in many price lists, but it can appear only once in the same price list.

## `NULL` and `UNIQUE`

In MySQL, a unique column may allow multiple `NULL` values because `NULL` represents an unknown value. If every value must be present and unique, combine both constraints:

```sql
email VARCHAR(254) NOT NULL UNIQUE
```

## Adding `UNIQUE` to an Existing Table

```sql
ALTER TABLE products
ADD CONSTRAINT uq_products_code UNIQUE (product_code);
```

This fails if duplicate non-null values already exist.

## Removing a Unique Constraint

A MySQL unique constraint is implemented using a unique index. Check the index name:

```sql
SHOW INDEX FROM products;
```

Then remove it:

```sql
ALTER TABLE products
DROP INDEX uq_products_code;
```

## Best Practices

- Use `UNIQUE` for alternate identifiers such as email, username, employee number, or product code.
- Add `NOT NULL` when the unique value is required.
- Use a composite unique constraint when uniqueness depends on a combination of columns.

---

# 3. `PRIMARY KEY`

A `PRIMARY KEY` uniquely identifies every row in a table.

## Properties

A primary key:

- Must be unique.
- Cannot contain `NULL`.
- Can contain one column or multiple columns.
- Allows only one primary key constraint per table.
- Is commonly referenced by foreign keys.
- Should generally be stable and not change often.

## Single-Column Primary Key

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);
```

## Named Primary Key

```sql
CREATE TABLE products (
    product_id INT NOT NULL,
    product_name VARCHAR(150) NOT NULL,
    CONSTRAINT pk_products PRIMARY KEY (product_id)
);
```

## Composite Primary Key

A primary key can consist of multiple columns:

```sql
CREATE TABLE order_items (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (order_id, product_id)
);
```

The combination of `order_id` and `product_id` identifies one product line within an order.

## Adding a Primary Key to an Existing Table

```sql
ALTER TABLE products
ADD CONSTRAINT pk_products PRIMARY KEY (product_id);
```

The column must contain no duplicates and no `NULL` values.

## Removing a Primary Key

```sql
ALTER TABLE products
DROP PRIMARY KEY;
```

Check foreign key dependencies before removing a primary key.

## Best Practices

- Give every important table a reliable primary key.
- Prefer a short, stable identifier.
- Do not use a name as a primary key when names can be duplicated or changed.
- Do not treat auto-increment values as row counts; deletions and failed inserts can create gaps.

---

# 4. `FOREIGN KEY`

A `FOREIGN KEY` connects a column or group of columns in one table to a key in another table.

It enforces **referential integrity**, which means a child row cannot refer to a nonexistent parent row.

## Parent and Child Tables

- The **parent table** contains the referenced key.
- The **child table** contains the foreign key.

Example:

```text
departments                 employees
------------                ----------------
department_id  <----------- department_id
```

Every employee can belong to a department, but the department must exist first.

## Basic Example

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT NOT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
);
```

This insert fails if department `99` does not exist:

```sql
INSERT INTO employees (employee_id, employee_name, department_id)
VALUES (1, 'Asha', 99);
```

## Foreign Key Requirements

- Referenced columns must be indexed and are commonly a primary key or unique key.
- Referencing and referenced columns should have compatible data types.
- Integer signedness should match, such as `INT` with `INT` or `INT UNSIGNED` with `INT UNSIGNED`.
- The parent table should exist before the child table is created.
- The relationship should represent a real business rule.

## Nullable Foreign Keys

A foreign key may be nullable when the relationship is optional:

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
);
```

Here, `department_id = NULL` means the employee is not currently assigned to a department. A non-null value must still refer to an existing department.

# 5. `DEFAULT`

The `DEFAULT` constraint supplies a value when an `INSERT` statement does not provide one.

## Syntax

```sql
column_name data_type DEFAULT default_value
```

## Example

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    quantity INT NOT NULL DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);
```

If a product is inserted without `quantity` or `is_active`, MySQL uses `0` and `TRUE`.

```sql
INSERT INTO products (product_id, product_name)
VALUES (1, 'Notebook');
```

The resulting values include:

```text
quantity: 0
is_active: 1
```

## Default Date and Time

```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    order_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

The current timestamp is automatically recorded when an order is created.

## Default Text

```sql
status VARCHAR(20) NOT NULL DEFAULT 'pending'
```

## Adding or Changing a Default

```sql
ALTER TABLE products
ALTER COLUMN quantity SET DEFAULT 0;
```

For compatibility across MySQL versions and definitions, you can also redefine the complete column:

```sql
ALTER TABLE products
MODIFY COLUMN quantity INT NOT NULL DEFAULT 0;
```

## Removing a Default

```sql
ALTER TABLE products
ALTER COLUMN quantity DROP DEFAULT;
```

Or redefine the column without a default:

```sql
ALTER TABLE products
MODIFY COLUMN quantity INT NOT NULL;
```

## `DEFAULT` and Explicit `NULL`

A default is generally used when the column is omitted from the insert. Explicitly inserting `NULL` is different:

```sql
INSERT INTO products (product_id, product_name, quantity)
VALUES (2, 'Pen', NULL);
```

If `quantity` is `NOT NULL`, this fails. The default value does not necessarily replace an explicitly supplied `NULL`.

## Best Practices

- Use defaults for sensible, predictable starting values.
- Use `DEFAULT 0` for counts or quantities when zero is meaningful.
- Use `DEFAULT CURRENT_TIMESTAMP` for creation times.
- Do not use a default to hide missing required information.

# 6. `CHECK`

A `CHECK` constraint requires values to satisfy a condition.

## Basic Syntax

```sql
column_name data_type CHECK (condition)
```

## Example: Valid Age

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100) NOT NULL,
    age INT CHECK (age BETWEEN 5 AND 100)
);
```

An age outside the allowed range is rejected.

## Named `CHECK` Constraint

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    CONSTRAINT chk_products_price CHECK (price >= 0),
    CONSTRAINT chk_products_quantity CHECK (quantity >= 0)
);
```

## Multiple-Column `CHECK`

A check constraint can compare columns:

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE,
    CONSTRAINT chk_employment_dates
        CHECK (end_date IS NULL OR end_date >= start_date)
);
```

The end date must be empty or on or after the start date.

## Adding a `CHECK` Constraint

```sql
ALTER TABLE products
ADD CONSTRAINT chk_products_price CHECK (price >= 0);
```

Existing rows must satisfy the condition when the constraint is added.

## Removing a `CHECK` Constraint

```sql
ALTER TABLE products
DROP CHECK chk_products_price;
```

Use the exact constraint name.

## Important Notes

- `CHECK` behavior depends on the MySQL version; modern MySQL versions enforce check constraints.
- A `CHECK` condition should be deterministic and based on row values.
- Use `CHECK` for rules that belong at the database level.
- Complex business processes may still need application logic, stored procedures, or triggers.

# 7. `AUTO_INCREMENT`

`AUTO_INCREMENT` automatically generates a new numeric value for a column when a row is inserted without an explicit value.

It is commonly used with an integer primary key.

## Example

```sql
CREATE TABLE departments (
    department_id INT UNSIGNED AUTO_INCREMENT,
    department_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (department_id)
);
```

Insert rows without specifying the ID:

```sql
INSERT INTO departments (department_name)
VALUES ('Computer Science');

INSERT INTO departments (department_name)
VALUES ('Physics');
```

MySQL generates IDs automatically.

## Important Properties

- The column must use a numeric type.
- It is commonly indexed as a primary key.
- Values normally increase, but gaps can occur.
- Deleting a row does not necessarily reuse its ID.
- Failed inserts or rolled-back transactions may consume numbers.
- It does not guarantee that values are consecutive.

## Reading the Generated ID

After an insert, applications can retrieve the generated ID using the relevant MySQL client API. In SQL tools, you can use:

```sql
SELECT LAST_INSERT_ID();
```

## Explicit Values

MySQL may allow an explicit value to be inserted into an auto-increment column, subject to constraints and configuration. Applications should generally allow MySQL to generate identifiers unless there is a clear reason to provide one.

## Best Practices

- Use `AUTO_INCREMENT` for surrogate numeric identifiers.
- Do not expose internal IDs as sensitive information without considering security implications.
- Do not rely on IDs being gap-free.
- Use `BIGINT UNSIGNED AUTO_INCREMENT` when a table may grow beyond the safe range of `INT`.

# 8. Foreign Key Actions

Foreign key actions define what happens to child rows when a referenced parent row is updated or deleted.

These actions are written in the foreign key definition:

```sql
FOREIGN KEY (child_column)
REFERENCES parent_table (parent_column)
ON DELETE action
ON UPDATE action
```

The requested actions are:

- `ON DELETE CASCADE`
- `ON DELETE SET NULL`
- `ON DELETE RESTRICT`
- `ON UPDATE CASCADE`

---

## 8.1 `ON DELETE CASCADE`

`ON DELETE CASCADE` automatically deletes related child rows when the parent row is deleted.

## Example: Departments and Employees

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT NOT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
        ON DELETE CASCADE
);
```

If a department is deleted, all employees assigned to it are deleted automatically.

## When to Use

Use `CASCADE` when child rows have no meaning without the parent, such as:

- Order items when an order is permanently deleted from a test system
- Enrollment details belonging only to a removed registration
- Temporary child records owned entirely by a parent

## Caution

Cascading deletes can remove many rows with one command. Do not use them merely for convenience when employees, financial records, or historical data must be retained.

---

## 8.2 `ON DELETE SET NULL`

`ON DELETE SET NULL` changes the child foreign key to `NULL` when the parent row is deleted.

## Example: Optional Department Assignment

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
        ON DELETE SET NULL
);
```

If a department is removed, employee records remain, but their `department_id` becomes `NULL`.

## Requirements

The child foreign key column must allow `NULL`:

```sql
department_id INT NULL
```

This action is useful when the child record should survive but its former parent is no longer available.

## Suitable Examples

- Employees remain after a department is closed.
- Orders remain after an optional sales representative is removed.
- Products remain after an optional category is deleted.

---

## 8.3 `ON DELETE RESTRICT`

`ON DELETE RESTRICT` prevents a parent row from being deleted while child rows refer to it.

## Example: Products and Orders

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_code VARCHAR(30) NOT NULL UNIQUE,
    product_name VARCHAR(150) NOT NULL
);

CREATE TABLE order_items (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL,
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id)
        REFERENCES products (product_id)
        ON DELETE RESTRICT
);
```

If an existing order item refers to a product, MySQL prevents deleting that product.

## When to Use

`RESTRICT` is suitable when historical or transactional data must remain valid, especially for:

- Products referenced by orders
- Departments containing employees
- Customers with invoices
- Accounts with financial transactions

## Benefit

It prevents accidental loss of relationships and forces the application or administrator to handle dependent records deliberately.

---

## 8.4 `ON UPDATE CASCADE`

`ON UPDATE CASCADE` automatically updates foreign key values in child rows when the referenced key value changes.

## Example

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    department_id INT NOT NULL,
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
        ON UPDATE CASCADE
);
```

If `departments.department_id` changes from `10` to `20`, related `employees.department_id` values are updated automatically.

## Important Design Note

Primary keys are usually designed to remain stable, so updates to primary key values should be uncommon. `ON UPDATE CASCADE` is useful when referenced keys may legitimately change, but it should not encourage frequent changes to identifiers.

---

# 9. Choosing Foreign Key Actions

| Situation | Suitable Action |
|---|---|
| Child has no meaning without parent | `ON DELETE CASCADE` |
| Child should remain but lose the relationship | `ON DELETE SET NULL` |
| Parent must not be removed while referenced | `ON DELETE RESTRICT` |
| Parent key changes should propagate | `ON UPDATE CASCADE` |

## Practical Decision Questions

Before choosing an action, ask:

1. Should the child record survive if the parent is deleted?
2. Would deleting the child destroy legal, financial, or historical information?
3. Is the relationship required or optional?
4. Can the foreign key column accept `NULL`?
5. Could one parent have thousands of child rows?
6. Is automatic deletion safe for this business process?
7. Should parent identifiers ever change?

# 10. Practical Database Design Example

The following example uses all requested constraints with practical tables.

```sql
CREATE DATABASE IF NOT EXISTS company_store_db;
USE company_store_db;

CREATE TABLE departments (
    department_id INT UNSIGNED AUTO_INCREMENT,
    department_code CHAR(5) NOT NULL,
    department_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (department_id),
    CONSTRAINT uq_departments_code UNIQUE (department_code),
    CONSTRAINT uq_departments_name UNIQUE (department_name)
);

CREATE TABLE employees (
    employee_id INT UNSIGNED AUTO_INCREMENT,
    employee_number VARCHAR(20) NOT NULL,
    employee_name VARCHAR(100) NOT NULL,
    email VARCHAR(254) NOT NULL,
    salary DECIMAL(12, 2) NOT NULL DEFAULT 0.00,
    department_id INT UNSIGNED NULL,
    hire_date DATE NOT NULL,
    end_date DATE NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (employee_id),
    CONSTRAINT uq_employees_number UNIQUE (employee_number),
    CONSTRAINT uq_employees_email UNIQUE (email),
    CONSTRAINT chk_employees_salary CHECK (salary >= 0),
    CONSTRAINT chk_employees_dates
        CHECK (end_date IS NULL OR end_date >= hire_date),
    CONSTRAINT fk_employees_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

CREATE TABLE students (
    student_id INT UNSIGNED AUTO_INCREMENT,
    student_number VARCHAR(20) NOT NULL,
    student_name VARCHAR(100) NOT NULL,
    email VARCHAR(254) NOT NULL,
    age INT NOT NULL,
    admission_date DATE NOT NULL DEFAULT (CURRENT_DATE),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (student_id),
    CONSTRAINT uq_students_number UNIQUE (student_number),
    CONSTRAINT uq_students_email UNIQUE (email),
    CONSTRAINT chk_students_age CHECK (age BETWEEN 5 AND 100)
);

CREATE TABLE products (
    product_id INT UNSIGNED AUTO_INCREMENT,
    product_code VARCHAR(30) NOT NULL,
    product_name VARCHAR(150) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    stock_quantity INT UNSIGNED NOT NULL DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (product_id),
    CONSTRAINT uq_products_code UNIQUE (product_code),
    CONSTRAINT chk_products_price CHECK (price >= 0)
);

CREATE TABLE orders (
    order_id BIGINT UNSIGNED AUTO_INCREMENT,
    customer_name VARCHAR(100) NOT NULL,
    order_status VARCHAR(20) NOT NULL DEFAULT 'pending',
    order_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (order_id),
    CONSTRAINT chk_orders_status
        CHECK (order_status IN ('pending', 'confirmed', 'shipped', 'cancelled'))
);

CREATE TABLE order_items (
    order_id BIGINT UNSIGNED NOT NULL,
    product_id INT UNSIGNED NOT NULL,
    quantity INT UNSIGNED NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL,
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT chk_order_items_quantity CHECK (quantity > 0),
    CONSTRAINT chk_order_items_price CHECK (unit_price >= 0),
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id)
        REFERENCES orders (order_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id)
        REFERENCES products (product_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);
```

## What This Example Demonstrates

### Departments

- `department_id` uses `PRIMARY KEY` and `AUTO_INCREMENT`.
- `department_code` and `department_name` use `UNIQUE`.
- `created_at` uses `DEFAULT CURRENT_TIMESTAMP`.
- Required fields use `NOT NULL`.

### Employees

- `employee_id` is an auto-generated primary key.
- Employee number and email must be unique.
- Salary cannot be negative because of `CHECK`.
- Employment dates must be logically ordered.
- `department_id` is an optional foreign key.
- If a department is deleted, employees remain and `department_id` becomes `NULL`.
- If a department ID changes, the employee reference changes automatically.

### Students

- Student ID is generated automatically.
- Student number and email are unique.
- Age must be between 5 and 100.
- Admission date and active status have defaults.

### Products

- Product code identifies a product in business terms and is unique.
- Price cannot be negative.
- Stock quantity defaults to zero and cannot be negative because it is unsigned.

### Orders and Order Items

- An order has an auto-generated `BIGINT` primary key.
- Order status has a default and a permitted set of values.
- `order_items` uses a composite primary key.
- Deleting an order deletes its order items with `ON DELETE CASCADE`.
- Deleting a product referenced by an order is prevented with `ON DELETE RESTRICT`.

# 11. Adding Constraints to Existing Tables

Constraints can be defined during table creation or added later.

## Add `NOT NULL`

```sql
ALTER TABLE employees
MODIFY COLUMN employee_name VARCHAR(100) NOT NULL;
```

## Add a Unique Constraint

```sql
ALTER TABLE employees
ADD CONSTRAINT uq_employees_email UNIQUE (email);
```

## Add a Primary Key

```sql
ALTER TABLE departments
ADD CONSTRAINT pk_departments PRIMARY KEY (department_id);
```

## Add a Foreign Key

```sql
ALTER TABLE employees
ADD CONSTRAINT fk_employees_department
    FOREIGN KEY (department_id)
    REFERENCES departments (department_id)
    ON DELETE SET NULL
    ON UPDATE CASCADE;
```

## Add a Default

```sql
ALTER TABLE products
ALTER COLUMN stock_quantity SET DEFAULT 0;
```

Or redefine the full column:

```sql
ALTER TABLE products
MODIFY COLUMN stock_quantity INT UNSIGNED NOT NULL DEFAULT 0;
```

## Add a Check Constraint

```sql
ALTER TABLE products
ADD CONSTRAINT chk_products_price CHECK (price >= 0);
```

## Remove a Foreign Key

```sql
ALTER TABLE employees
DROP FOREIGN KEY fk_employees_department;
```

## Remove a Check Constraint

```sql
ALTER TABLE products
DROP CHECK chk_products_price;
```

## Remove a Unique Constraint

```sql
ALTER TABLE employees
DROP INDEX uq_employees_email;
```

Always use the exact constraint or index name shown by `SHOW CREATE TABLE`.

# 12. Inspecting Constraints in MySQL

## View the Complete Table Definition

```sql
SHOW CREATE TABLE employees;
```

This displays columns, primary keys, unique keys, foreign keys, check constraints, indexes, and default definitions.

## View Table Columns

```sql
DESCRIBE employees;
```

The result shows `NULL`, `Key`, `Default`, and `Extra` information.

## View Indexes

```sql
SHOW INDEX FROM employees;
```

This helps inspect primary and unique indexes.

## List Constraints

```sql
SELECT
    TABLE_NAME,
    CONSTRAINT_NAME,
    CONSTRAINT_TYPE
FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = DATABASE();
```

## List Foreign Key Relationships

```sql
SELECT
    TABLE_NAME,
    CONSTRAINT_NAME,
    COLUMN_NAME,
    REFERENCED_TABLE_NAME,
    REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND REFERENCED_TABLE_NAME IS NOT NULL;
```

# 13. Common Constraint Errors

## Duplicate Entry for a Unique Key

**Cause:** An inserted or updated value already exists in a primary or unique key.

**Example:** Two employees use the same email.

**Solution:** Check existing values and decide whether the new value should be changed or whether the uniqueness rule is incorrect.

## Cannot Be Null

**Cause:** A required `NOT NULL` column was omitted or given `NULL`.

**Solution:** Supply a valid value or decide whether the column should be optional.

## Cannot Add or Update a Child Row

**Cause:** A foreign key value does not match a row in the parent table.

**Solution:** Insert the parent first, use a valid parent key, or use `NULL` only if the relationship is optional.

## Cannot Delete or Update a Parent Row

**Cause:** Child rows still refer to the parent and the foreign key action prevents the operation.

**Solution:** Update or delete child rows deliberately, or choose a different foreign key action if the business rule allows it.

## Check Constraint Is Violated

**Cause:** A value does not satisfy a `CHECK` condition.

**Solution:** Correct the value or review whether the condition represents the real business rule.

## Data Truncated or Invalid Default

**Cause:** The default value does not match the column's type or restrictions.

**Solution:** Use a valid default and verify the column definition.

# 14. Constraint Design Guidelines

- Use `NOT NULL` for values that every valid row must contain.
- Use `PRIMARY KEY` to give each row a stable identity.
- Use `UNIQUE` for alternate identifiers and business-level uniqueness.
- Use `FOREIGN KEY` to enforce relationships between tables.
- Use `DEFAULT` for safe and meaningful starting values.
- Use `CHECK` for simple row-level business rules.
- Use `AUTO_INCREMENT` when the database should generate numeric identifiers.
- Name constraints clearly and consistently.
- Match foreign key types exactly where possible.
- Select `CASCADE` only when automatic child deletion is safe.
- Use `SET NULL` only when the child relationship is optional.
- Use `RESTRICT` to protect history and prevent accidental parent deletion.
- Test constraints with both valid and invalid data.
- Back up important data before changing or removing constraints.
- Remember that constraints protect data, but they do not replace authorization, auditing, or application validation.

# Final Revision Summary

- A constraint is a database rule that protects data quality.
- `NOT NULL` requires a value.
- `UNIQUE` prevents duplicate values or duplicate combinations.
- `PRIMARY KEY` uniquely identifies every row and cannot be `NULL`.
- `FOREIGN KEY` connects a child table to a parent table.
- `DEFAULT` supplies a value when an insert omits a column.
- `CHECK` rejects values that do not satisfy a condition.
- `AUTO_INCREMENT` generates numeric identifiers automatically.
- `ON DELETE CASCADE` deletes related children automatically.
- `ON DELETE SET NULL` keeps the child but removes its parent reference.
- `ON DELETE RESTRICT` prevents deleting a parent that still has children.
- `ON UPDATE CASCADE` propagates changes to referenced key values.
- Use constraints together to enforce complete, accurate, and consistent database rules.
