# 3. MySQL Data Types

## Learning Objectives

After completing this module, you should be able to:

- Identify common MySQL numeric, string, date and time, and boolean data types.
- Choose data types that match the meaning and size of stored values.
- Compare `CHAR` and `VARCHAR`.
- Compare `DATETIME` and `TIMESTAMP`.
- Avoid common data type design mistakes.

---

## 1. What Is a Data Type?

A **data type** specifies what kind of value a column can store and how MySQL should interpret that value.

A data type affects:

- The values that can be stored
- The amount of storage used
- Whether calculations are possible
- How values are compared and sorted
- The accuracy of stored values
- Query and index performance
- Whether invalid values are rejected

### Example

```sql
CREATE TABLE products (
    product_id INT,
    product_name VARCHAR(100),
    price DECIMAL(10, 2),
    available BOOLEAN,
    created_on DATE
);
```

In this table:

- `product_id` stores whole numbers.
- `product_name` stores variable-length text.
- `price` stores an exact amount with two decimal places.
- `available` stores a true or false value.
- `created_on` stores a calendar date.

# Part 1: Numeric Data Types

Numeric types store numbers. Choose a numeric type based on whether the value is a whole number or a number with a fractional part, and whether exact precision is important.

## 2. `INT`

`INT` stores signed or unsigned whole numbers.

### Syntax

```sql
column_name INT
```

### Common Range

For a signed `INT`, the range is approximately:

```text
-2,147,483,648 to 2,147,483,647
```

For an unsigned `INT`, the range is approximately:

```text
0 to 4,294,967,295
```

### Example

```sql
CREATE TABLE students (
    student_id INT,
    age INT
);
```

### Suitable Uses

- IDs
- Counts
- Ages
- Quantities
- Marks
- Status codes

### Unsigned `INT`

If negative values are not meaningful, use `UNSIGNED`:

```sql
quantity INT UNSIGNED;
```

This prevents negative quantities and increases the positive range.

### Important Note

Do not use `INT` for values such as phone numbers or postal codes merely because they contain digits. Those values are identifiers, not quantities, and may contain leading zeroes or symbols.

---

## 3. `BIGINT`

`BIGINT` stores very large whole numbers. It uses more storage than `INT` but provides a much larger range.

### Common Range

For a signed `BIGINT`, the range is approximately:

```text
-9,223,372,036,854,775,808
through
9,223,372,036,854,775,807
```

For an unsigned `BIGINT`, the maximum is approximately:

```text
18,446,744,073,709,551,615
```

### Example

```sql
CREATE TABLE events (
    event_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    event_count BIGINT UNSIGNED
);
```

### Suitable Uses

- Very large IDs
- Large counters
- High-volume event systems
- Timestamps or numeric values outside the `INT` range
- Large financial or scientific counts when a whole number is required

### Design Advice

Use `BIGINT` when the expected value may exceed the safe range of `INT`. Do not use it automatically for every integer column because larger types use more storage and may make indexes larger.

---

## 4. `DECIMAL`

`DECIMAL` stores exact fixed-point numbers. It is the preferred type for values where exact precision matters.

### Syntax

```sql
DECIMAL(total_digits, decimal_digits)
```

- The first number is the total number of digits.
- The second number is the number of digits after the decimal point.

### Example

```sql
price DECIMAL(10, 2)
```

This can store values with up to 10 total digits, including 2 digits after the decimal point. For example:

```text
99999999.99
```

### Suitable Uses

- Prices
- Salaries
- Tax amounts
- Account balances
- Measurements requiring exact decimal precision

### Example Table

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL
);
```

### Why Use `DECIMAL` for Money?

Floating-point values are stored approximately. Small rounding differences can occur during calculations. Financial values usually require exact decimal behavior, so `DECIMAL` is safer than `FLOAT` or `DOUBLE` for money.

### Choosing Precision

Choose a precision and scale that match the real requirement:

```sql
salary DECIMAL(12, 2)
percentage DECIMAL(5, 2)
```

`DECIMAL(5, 2)` can represent values such as `999.99`, but it may not be suitable for a percentage if values above 100 are invalid. Add a suitable constraint when needed.

---

## 5. `FLOAT`

`FLOAT` stores approximate single-precision floating-point numbers.

### Example

```sql
latitude FLOAT;
```

### Suitable Uses

- Scientific values where a small approximation is acceptable
- Measurements from sensors
- Approximate calculations
- Values where storage size matters more than exact precision

### Limitations

- Values may be rounded during storage or calculation.
- Exact equality comparisons can be unreliable.
- It should generally not be used for currency or accounting values.

### Example of a Risky Comparison

```sql
WHERE measured_value = 0.1
```

For an approximate type, the stored value may not be exactly equal to the number written in the query. Use a tolerance or an exact type when exact comparison is required.

---

## 6. `DOUBLE`

`DOUBLE` stores approximate double-precision floating-point numbers. It usually provides more precision and range than `FLOAT`, but it is still approximate.

### Example

```sql
longitude DOUBLE;
```

### Suitable Uses

- Scientific and engineering calculations
- Large or high-precision approximate measurements
- Statistical calculations
- Values where a floating-point approximation is acceptable

### `FLOAT` vs `DOUBLE`

| Feature | `FLOAT` | `DOUBLE` |
|---|---|---|
| Precision | Lower | Higher |
| Storage | Usually smaller | Usually larger |
| Range | Smaller | Larger |
| Accuracy | Approximate | Approximate |
| Suitable for money | No | No, generally |
| Suitable for measurements | Yes | Yes, when more precision is needed |

### Numeric Type Selection

| Requirement | Recommended Type |
|---|---|
| Ordinary whole number | `INT` |
| Very large whole number | `BIGINT` |
| Exact price or amount | `DECIMAL` |
| Approximate measurement with modest precision | `FLOAT` |
| Approximate measurement needing more precision | `DOUBLE` |

# Part 2: String Data Types

String types store character data such as names, addresses, codes, descriptions, and messages.

## 7. `CHAR`

`CHAR(n)` stores a fixed-length string of up to `n` characters.

### Syntax

```sql
column_name CHAR(length)
```

### Example

```sql
country_code CHAR(2);
```

A country code such as `IN`, `US`, or `GB` has a predictable length, making `CHAR(2)` suitable.

### Suitable Uses

- Fixed-length codes
- Country codes
- State or department codes
- Fixed-format identifiers
- Values that are nearly always the same length

### Characteristics

- Declared length is fixed.
- MySQL may pad stored values to the declared length.
- Trailing spaces may be handled according to MySQL string comparison rules.
- A very large `CHAR` length wastes space when most values are short.

---

## 8. `VARCHAR`

`VARCHAR(n)` stores a variable-length string of up to `n` characters.

### Syntax

```sql
column_name VARCHAR(length)
```

### Example

```sql
student_name VARCHAR(100);
email VARCHAR(254);
```

A person's name or email address can have different lengths, so `VARCHAR` is usually appropriate.

### Suitable Uses

- Names
- Email addresses
- Phone numbers
- Usernames
- Addresses
- Product names
- URLs
- Short descriptions

### Characteristics

- Stores only the characters needed, along with length information.
- The maximum length should be chosen based on the expected data.
- A very large maximum does not mean every row uses that much space, but it may affect row and index limits.
- Use a meaningful maximum instead of always choosing an unnecessarily large value.

---

## 9. `TEXT`

`TEXT` stores variable-length text that is generally larger than ordinary `VARCHAR` values.

### Example

```sql
description TEXT;
article_body TEXT;
```

### Suitable Uses

- Long descriptions
- Comments
- Articles
- Notes
- Message content
- Document text

### Common Text Sizes

MySQL provides several text types for different maximum sizes:

- `TINYTEXT`
- `TEXT`
- `MEDIUMTEXT`
- `LONGTEXT`

### Limitations and Considerations

- Use `TEXT` when the content is genuinely long.
- Indexing a `TEXT` column may require a prefix length or a full-text index, depending on the use case.
- `TEXT` is not always the best replacement for a large `VARCHAR`.
- Store files such as images and videos outside the database in many application designs, keeping a file path or URL in the database instead.

---

## 10. `CHAR` vs `VARCHAR`

Both types store strings, but they are designed for different data patterns.

| Feature | `CHAR(n)` | `VARCHAR(n)` |
|---|---|---|
| Length | Fixed maximum length | Variable maximum length |
| Storage behavior | Fixed-length values | Stores the actual length plus value |
| Best for | Values with predictable length | Values with varying length |
| Examples | `CHAR(2)` country code | `VARCHAR(100)` name |
| Space efficiency | Can waste space for short values | Usually more efficient for varying lengths |
| Flexibility | Less flexible | More flexible |

### Examples

Use `CHAR`:

```sql
country_code CHAR(2)
```

Use `VARCHAR`:

```sql
full_name VARCHAR(150)
```

### Decision Rule

- Use **`CHAR`** when every value is the same length or nearly the same length.
- Use **`VARCHAR`** when values have different lengths.
- Use **`TEXT`** for genuinely long text that does not need ordinary short-string behavior.

### Common Mistake

Do not use `CHAR(255)` for every text column. If most values are short and variable, `VARCHAR` is usually a better choice.

# Part 3: Date and Time Data Types

Date and time types store calendar dates, times, or both.

## 11. `DATE`

`DATE` stores a calendar date in the form `YYYY-MM-DD`.

### Example

```sql
birth_date DATE;
```

Example value:

```text
2005-04-12
```

### Suitable Uses

- Birth dates
- Admission dates
- Invoice dates
- Holiday dates
- Due dates
- Dates where time of day is not important

### Example

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100),
    birth_date DATE,
    joining_date DATE
);
```

---

## 12. `TIME`

`TIME` stores a time of day or a time interval.

### Syntax and Example

```sql
opening_time TIME;
```

Example value:

```text
09:30:00
```

### Suitable Uses

- Store opening and closing times
- Appointment times when the date is stored separately
- Duration-like values that need hours, minutes, and seconds

### Example

```sql
CREATE TABLE schedules (
    schedule_id INT PRIMARY KEY,
    start_time TIME,
    end_time TIME
);
```

If both a date and a time are needed together, use `DATETIME` or `TIMESTAMP` instead.

---

## 13. `DATETIME`

`DATETIME` stores both a date and a time.

### Example

```sql
created_at DATETIME;
```

Example value:

```text
2026-09-09 14:30:00
```

### Suitable Uses

- Appointments
- Events
- Order dates
- Schedules
- Historical records where the original local date and time should remain unchanged

### Characteristics

- Represents a calendar date and time.
- Does not automatically convert the value based on the session time zone in the same way as `TIMESTAMP`.
- Has a large date range compared with `TIMESTAMP`.
- Takes more storage than a simple `DATE` because it includes time.

### Example

```sql
CREATE TABLE appointments (
    appointment_id INT PRIMARY KEY,
    appointment_time DATETIME NOT NULL
);
```

---

## 14. `TIMESTAMP`

`TIMESTAMP` stores a date and time and is commonly used for event times such as creation and modification timestamps.

### Example

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP;
```

### Automatic Update Example

```sql
updated_at TIMESTAMP
    DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP;
```

This sets the creation time automatically and updates `updated_at` whenever the row changes.

### Suitable Uses

- Record creation times
- Record update times
- Audit events
- System-generated event times
- Data where time zone conversion is useful

### Characteristics

- MySQL commonly converts `TIMESTAMP` values between the session time zone and UTC during storage and retrieval.
- It has a more limited range than `DATETIME`.
- It is commonly used for automatic timestamps.
- Exact automatic behavior depends on the MySQL version and column definition.

---

## 15. `YEAR`

`YEAR` stores a year value.

### Example

```sql
manufacture_year YEAR;
```

Example value:

```text
2026
```

### Suitable Uses

- Manufacture year
- Graduation year
- Financial year label
- Model year

### Important Note

Use `YEAR` only when the year by itself is meaningful. If an exact date is required, use `DATE`. If an exact date and time are required, use `DATETIME` or `TIMESTAMP`.

---

## 16. `DATETIME` vs `TIMESTAMP`

Both types store a date and time, but they have different behavior and use cases.

| Feature | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| Stores | Date and time | Date and time |
| Time zone conversion | Generally does not convert for session time zones | Commonly converts between session time zone and UTC |
| Range | Larger range | More limited range |
| Automatic current time | Can be configured in modern MySQL versions | Commonly used for automatic current timestamps |
| Best for | Fixed calendar events and historical local times | System events and audit timestamps |
| Time zone sensitivity | Useful when displayed time must remain as entered | Useful when the same moment is viewed in multiple time zones |
| Storage | Usually larger | Usually smaller |

### Use `DATETIME` When

- The stored local date and time must remain exactly as entered.
- The value represents an appointment or scheduled event.
- The date may be outside the normal `TIMESTAMP` range.
- You do not want automatic time zone conversion.

Example:

```sql
appointment_start DATETIME NOT NULL
```

### Use `TIMESTAMP` When

- The value represents the moment a row was created or updated.
- The same event may be viewed by users in different time zones.
- You want a default such as `CURRENT_TIMESTAMP`.
- You are recording system or audit events.

Example:

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

### Time Zone Example

Suppose an application records an event at 10:00 UTC and users view it in two different time zones. A `TIMESTAMP` can represent the same instant and display it according to the session time zone. A `DATETIME` stores a calendar value without automatically representing a time-zone conversion.

### Design Rule

- For a **moment in time**, especially an automatically generated event time, prefer `TIMESTAMP`.
- For a **calendar date and time entered as a business value**, such as a meeting scheduled for a local office, prefer `DATETIME`.

Always document the time zone used by the application. A database column alone cannot fix an unclear time-zone policy.

# Part 4: Other Data Types

## 17. `BOOLEAN`

`BOOLEAN` represents a true or false value.

### Example

```sql
is_active BOOLEAN;
```

In MySQL, `BOOLEAN` is treated as a synonym for `TINYINT(1)`:

- `0` generally represents false.
- `1` generally represents true.

### Creating a Boolean Column

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(100) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);
```

### Inserting Boolean Values

```sql
INSERT INTO users (user_id, username, is_active)
VALUES (1, 'asha', TRUE);
```

You can also use `1` and `0`:

```sql
INSERT INTO users (user_id, username, is_active)
VALUES (2, 'ravi', 0);
```

### Querying Boolean Values

```sql
SELECT *
FROM users
WHERE is_active = TRUE;
```

### Important Notes

- MySQL does not have a separate storage type that behaves like a strict Boolean in the same way in all contexts.
- If a column must allow only `0` and `1`, add a suitable constraint where supported by your MySQL version and design.
- Use `BOOLEAN` when the meaning is genuinely yes/no or true/false.

# Part 5: Choosing the Appropriate Data Type

Choosing a data type is a design decision. The type should match the meaning of the value, its expected range, its precision, and how it will be queried.

## 18. General Selection Rules

### Rule 1: Choose by Meaning, Not Appearance

A phone number contains digits but is not used for arithmetic. Store it as text:

```sql
phone_number VARCHAR(20)
```

Do not use:

```sql
phone_number BIGINT
```

A numeric type can remove leading zeroes and cannot naturally represent symbols such as `+`, spaces, or hyphens.

### Rule 2: Choose the Smallest Safe Numeric Type

Use a type large enough for the expected values, but do not choose a huge type without a reason.

| Example Value | Suitable Type |
|---|---|
| Age | `TINYINT` or `INT` |
| Product quantity | `INT UNSIGNED` |
| Very large event ID | `BIGINT UNSIGNED` |
| Product price | `DECIMAL(10,2)` |
| Scientific approximation | `DOUBLE` |

### Rule 3: Use Exact Types for Exact Values

Use `DECIMAL` for money and accounting values:

```sql
balance DECIMAL(15, 2)
```

Use `FLOAT` or `DOUBLE` for approximate scientific or measurement data when small rounding differences are acceptable.

### Rule 4: Choose a Realistic String Length

Use a length that reflects the requirement:

```sql
username VARCHAR(50)
email VARCHAR(254)
country_code CHAR(2)
```

Do not choose an arbitrary very large length for every string column.

### Rule 5: Use `TEXT` for Long Text

Use `VARCHAR` for ordinary names, codes, and short descriptions. Use `TEXT` for long articles, comments, or notes.

### Rule 6: Store Dates and Times According to Their Meaning

- Date only: `DATE`
- Time only: `TIME`
- Local date and time as a business value: `DATETIME`
- System event timestamp: `TIMESTAMP`
- Year only: `YEAR`

### Rule 7: Consider Constraints Alongside Types

A data type defines what kind of value can be stored. A constraint defines additional rules.

```sql
age INT CHECK (age BETWEEN 0 AND 130)
```

The type says that `age` is a whole number. The check limits it to a reasonable range.

### Rule 8: Consider Indexing

Columns used for searching, joining, sorting, or uniqueness may be indexed. Large string and text values can make indexes larger, so choose types and lengths carefully.

### Rule 9: Consider Future Growth

If an ID may eventually exceed the range of `INT`, choose `BIGINT` at the beginning. Changing a type later can require a migration and may affect related tables.

### Rule 10: Consider Nullability

Decide whether a value is required:

```sql
email VARCHAR(254) NOT NULL
```

or optional:

```sql
middle_name VARCHAR(100) NULL
```

`NULL` means the value is unknown or not provided. It is not the same as an empty string or zero.

## 19. Data Type Decision Table

| Data Requirement | Recommended Type |
|---|---|
| Small whole number | `INT` or a smaller integer type |
| Very large whole number | `BIGINT` |
| Currency or exact amount | `DECIMAL` |
| Approximate measurement | `FLOAT` or `DOUBLE` |
| Fixed-length code | `CHAR` |
| Variable-length short text | `VARCHAR` |
| Long text | `TEXT` |
| Calendar date | `DATE` |
| Time of day or duration | `TIME` |
| Local date and time | `DATETIME` |
| Automatic event time | `TIMESTAMP` |
| Year only | `YEAR` |
| True or false | `BOOLEAN` |

# Part 6: Complete Example

The following table demonstrates several data types in one design.

```sql
CREATE TABLE product_catalog (
    product_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    product_code CHAR(8) NOT NULL UNIQUE,
    product_name VARCHAR(150) NOT NULL,
    description TEXT,
    price DECIMAL(10, 2) NOT NULL,
    weight_kg DOUBLE,
    quantity INT UNSIGNED NOT NULL DEFAULT 0,
    is_available BOOLEAN NOT NULL DEFAULT TRUE,
    manufacture_year YEAR,
    available_from DATE,
    opening_time TIME,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME
);
```

### Why These Types Were Chosen

- `product_id BIGINT UNSIGNED`: Allows many positive product IDs.
- `product_code CHAR(8)`: Product codes have a fixed length.
- `product_name VARCHAR(150)`: Names vary in length.
- `description TEXT`: Descriptions may be long.
- `price DECIMAL(10, 2)`: Price requires exact decimal precision.
- `weight_kg DOUBLE`: Measurement may be approximate.
- `quantity INT UNSIGNED`: Quantity cannot be negative.
- `is_available BOOLEAN`: Represents true or false.
- `manufacture_year YEAR`: Only the year is needed.
- `available_from DATE`: Only the calendar date is needed.
- `opening_time TIME`: Only the time is needed.
- `created_at TIMESTAMP`: Records the system creation moment.
- `updated_at DATETIME`: Stores an explicitly managed update date and time.

# Part 7: Common Mistakes

## Mistake 1: Using Floating Point for Money

Avoid:

```sql
price FLOAT
```

Prefer:

```sql
price DECIMAL(10, 2)
```

## Mistake 2: Storing Phone Numbers as Integers

Avoid:

```sql
phone BIGINT
```

Prefer:

```sql
phone VARCHAR(20)
```

Phone numbers are identifiers and may contain a country code, leading zero, spaces, or symbols.

## Mistake 3: Using `CHAR` for All Text

`CHAR` is appropriate for fixed-length values, not for every string. Use `VARCHAR` for values whose lengths vary.

## Mistake 4: Using `TEXT` for Every String

`TEXT` is intended for long content. Ordinary names, codes, and emails are usually better represented by `VARCHAR` with a meaningful length.

## Mistake 5: Storing Dates as Strings

Avoid:

```sql
birth_date VARCHAR(20)
```

Prefer:

```sql
birth_date DATE
```

Date types support date functions, validation, sorting, and date arithmetic.

## Mistake 6: Using `DATETIME` and `TIMESTAMP` Without a Time-Zone Policy

Decide whether the application stores local time, UTC, or another standard. Document the decision and use it consistently.

## Mistake 7: Choosing a Type Only from Current Data

A value may fit today but grow later. Consider future values, maximum counts, and application requirements before finalizing a type.

# Final Revision Summary

- A data type controls the kind of value a column stores.
- Use `INT` for ordinary whole numbers and `BIGINT` for very large whole numbers.
- Use `DECIMAL` for exact values such as money.
- Use `FLOAT` and `DOUBLE` for approximate values.
- Use `CHAR` for fixed-length strings and `VARCHAR` for variable-length strings.
- Use `TEXT` for long text.
- Use `DATE` for a date, `TIME` for a time, and `YEAR` for a year.
- Use `DATETIME` for a date and time that should remain a calendar value.
- Use `TIMESTAMP` for system events and values where time-zone conversion is useful.
- MySQL `BOOLEAN` is commonly represented as `TINYINT(1)`.
- Choose a type based on meaning, range, precision, length, indexing, future growth, and nullability.
- Never choose a data type only because the value appears numeric; phone numbers and postal codes are usually text identifiers.
