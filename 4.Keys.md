# 4. Keys in DBMS and MySQL

## Why Keys Are Important

**Keys** are one of the most important concepts in relational database design. A key is a column or group of columns used to identify rows, enforce uniqueness, and connect tables.

Keys help a database answer three essential questions:

1. **Which row is this?**
2. **Can two rows have the same identifying value?**
3. **How is one table related to another table?**

Without well-designed keys:

- Duplicate records can be created.
- Rows may be difficult to identify or update.
- Relationships between tables may become invalid.
- Data consistency becomes difficult to maintain.
- Queries and joins become less reliable.

This chapter explains the major types of keys and how to implement them in MySQL.

# 1. What Is a Key?

A **key** is an attribute or set of attributes used to identify, distinguish, or relate records in a database table.

Consider this `students` table:

| student_id | email | student_name | department |
|---:|---|---|---|
| 101 | asha@example.com | Asha | Computer Science |
| 102 | ravi@example.com | Ravi | Physics |

In this table:

- `student_id` can identify each student.
- `email` may also uniquely identify each student.
- `student_name` may not be unique because two students can have the same name.

A key can consist of:

- **One column**, such as `student_id`.
- **Multiple columns**, such as `(student_id, course_id)` in an enrollment table.

---

# 2. Super Key

A **super key** is any column or combination of columns that uniquely identifies each row in a table.

A super key may contain more columns than necessary.

## Example

Consider:

| student_id | email | student_name |
|---:|---|---|
| 101 | asha@example.com | Asha |
| 102 | ravi@example.com | Ravi |

Possible super keys include:

- `{student_id}`
- `{email}`
- `{student_id, email}`
- `{student_id, student_name}`
- `{email, student_name}`
- `{student_id, email, student_name}`

Each set uniquely identifies a row. However, some sets contain unnecessary attributes.

## Important Characteristic

A super key only needs to guarantee uniqueness. It does **not** need to be minimal.

For example:

```text
{student_id, student_name}
```

is a super key if `student_id` alone is already unique, but `student_name` is unnecessary.

## Formal Definition

For a relation or table $R$, a set of attributes $K$ is a super key if no two rows in $R$ have the same values for all attributes in $K$.

## Example in MySQL Terms

If `student_id` is a primary key, then these combinations are also logically super keys:

- `student_id`
- `student_id, student_name`
- `student_id, email`

The extra columns do not make the identifier more useful, but the combinations still uniquely identify each row.

---

# 3. Candidate Key

A **candidate key** is a minimal super key. It uniquely identifies each row, and no attribute can be removed without losing uniqueness.

## Example

Suppose both `student_id` and `email` are unique:

| student_id | email | student_name |
|---:|---|---|
| 101 | asha@example.com | Asha |
| 102 | ravi@example.com | Ravi |

Possible candidate keys are:

- `{student_id}`
- `{email}`

The combination `{student_id, email}` is not a candidate key because it is not minimal. Either column alone is sufficient.

## Properties of a Candidate Key

A candidate key should be:

- **Unique:** No two rows have the same key value.
- **Minimal:** No attribute can be removed while preserving uniqueness.
- **Stable enough:** It should not change unnecessarily.
- **Non-null in practical use:** A row must have an identifying value.

## Choosing a Candidate Key

Good candidate keys are usually:

- Unique for every row
- Short and efficient
- Stable over time
- Always available
- Not dependent on changeable personal information

For example, a generated student ID is often a better candidate key than a name because names can be duplicated or changed.

---

# 4. Primary Key

A **primary key** is the candidate key selected as the main identifier for rows in a table.

A table can have many candidate keys but only one primary key constraint.

## Example

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    email VARCHAR(254) UNIQUE NOT NULL,
    student_name VARCHAR(100) NOT NULL
);
```

Here:

- `student_id` is the primary key.
- `email` is another unique identifier and can be considered an alternate key.
- Each `student_id` must be unique.
- `student_id` cannot be `NULL`.

## Properties of a Primary Key

A primary key:

- Uniquely identifies each row.
- Cannot contain `NULL` values.
- Has only one primary key constraint per table.
- Can contain one column or multiple columns.
- Is commonly referenced by foreign keys in other tables.
- Should usually be stable and rarely changed.

## Creating a Primary Key During Table Creation

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100) NOT NULL
);
```

## Creating a Named Primary Key Constraint

```sql
CREATE TABLE students (
    student_id INT NOT NULL,
    student_name VARCHAR(100) NOT NULL,
    CONSTRAINT pk_students PRIMARY KEY (student_id)
);
```

Naming constraints makes database definitions easier to understand and maintain.

## Adding a Primary Key to an Existing Table

```sql
ALTER TABLE students
ADD CONSTRAINT pk_students PRIMARY KEY (student_id);
```

Before running this command:

- `student_id` must not contain `NULL` values.
- Every `student_id` value must be unique.
- The column definition should be suitable for indexing.

## Removing a Primary Key

```sql
ALTER TABLE students
DROP PRIMARY KEY;
```

Do this only after checking whether other tables use the primary key through foreign keys.

## Auto-Increment Primary Key

MySQL can automatically generate integer IDs:

```sql
CREATE TABLE students (
    student_id INT UNSIGNED AUTO_INCREMENT,
    student_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (student_id)
);
```

When inserting a row, the ID can be omitted:

```sql
INSERT INTO students (student_name)
VALUES ('Asha');
```

MySQL generates the next available auto-increment value according to its rules.

### Auto-Increment Notes

- `AUTO_INCREMENT` is commonly used for surrogate numeric identifiers.
- Values may have gaps after deletions or rolled-back inserts.
- An ID value should not be treated as a count of rows.
- The key should identify a row, not carry business meaning unless the design specifically requires it.

# 5. Foreign Key

A **foreign key** is a column or group of columns in one table that refers to a candidate key, usually the primary key, in another table.

Foreign keys represent relationships and enforce **referential integrity**.

## Parent and Child Tables

- The table containing the referenced key is the **parent table** or referenced table.
- The table containing the foreign key is the **child table** or referencing table.

Example:

```text
customers                orders
-----------              ----------------
customer_id  <---------- customer_id
name                       order_id
                           order_date
```

Each order must refer to an existing customer.

## Example in MySQL

```sql
CREATE TABLE customers (
    customer_id INT UNSIGNED AUTO_INCREMENT,
    customer_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (customer_id)
);

CREATE TABLE orders (
    order_id INT UNSIGNED AUTO_INCREMENT,
    customer_id INT UNSIGNED NOT NULL,
    order_date DATE NOT NULL,
    PRIMARY KEY (order_id),
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id)
);
```

## How the Foreign Key Works

A value inserted into `orders.customer_id` must match an existing value in `customers.customer_id`, unless the foreign key column allows `NULL` and the value is `NULL`.

This is invalid if customer `999` does not exist:

```sql
INSERT INTO orders (customer_id, order_date)
VALUES (999, '2026-09-09');
```

The foreign key protects the database from an order referring to a nonexistent customer.

## Foreign Key with a Composite Reference

A foreign key can contain multiple columns when it references a composite key:

```sql
FOREIGN KEY (student_id, semester_id)
REFERENCES student_semesters (student_id, semester_id)
```

The number, order, and compatible data types of the referencing and referenced columns must match appropriately.

## Foreign Key Actions

Foreign key actions control what happens when a referenced parent row is updated or deleted.

### `ON DELETE CASCADE`

Deletes related child rows automatically:

```sql
CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON DELETE CASCADE
```

Use this only when child records should not exist without the parent.

### `ON DELETE SET NULL`

Sets the foreign key to `NULL` when the parent is deleted:

```sql
customer_id INT UNSIGNED NULL,
CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON DELETE SET NULL
```

The foreign key column must allow `NULL`.

### `ON DELETE RESTRICT`

Prevents deletion of the parent while related child rows exist. This is a common protective behavior.

### `ON UPDATE CASCADE`

Updates child foreign key values when the referenced parent key changes:

```sql
CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON UPDATE CASCADE
```

Changing primary key values is usually avoided, but the action may be useful in particular designs.

## Foreign Key Requirements

For a reliable foreign key relationship:

- The referenced columns must be indexed.
- The referenced columns are commonly a primary key or unique key.
- The corresponding columns should have compatible data types.
- Signed and unsigned integer definitions should match.
- The storage engine and database configuration must support foreign keys.
- The relationship should represent a real business rule.

## Viewing Foreign Keys

Use:

```sql
SHOW CREATE TABLE orders;
```

You can also inspect metadata using `INFORMATION_SCHEMA` when detailed database administration is required.

# 6. Alternate Key

An **alternate key** is a candidate key that was not selected as the primary key.

## Example

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_number VARCHAR(20) UNIQUE NOT NULL,
    email VARCHAR(254) UNIQUE NOT NULL,
    employee_name VARCHAR(100) NOT NULL
);
```

Suppose all of these can uniquely identify an employee:

- `employee_id`
- `employee_number`
- `email`

If `employee_id` is chosen as the primary key, then `employee_number` and `email` are alternate keys.

## Implementing an Alternate Key

In MySQL, an alternate key is commonly implemented using a `UNIQUE` constraint:

```sql
ALTER TABLE employees
ADD CONSTRAINT uq_employees_employee_number
UNIQUE (employee_number);
```

or:

```sql
ALTER TABLE employees
ADD CONSTRAINT uq_employees_email
UNIQUE (email);
```

## Important Point

An alternate key is a relational design concept. The database enforces it through a unique constraint or unique index.

An alternate key is not the same as a foreign key. It identifies a row in its own table, while a foreign key refers to a row in another table.

# 7. Composite Key

A **composite key** is a key made up of two or more columns.

It is used when no single column is sufficient to identify a row, but a combination of columns is unique.

## Example: Student Enrollments

A student can enroll in many courses, and a course can contain many students. The `enrollments` table can use both `student_id` and `course_id` to identify one enrollment.

```sql
CREATE TABLE enrollments (
    student_id INT UNSIGNED NOT NULL,
    course_id INT UNSIGNED NOT NULL,
    enrollment_date DATE NOT NULL,
    grade CHAR(2),
    PRIMARY KEY (student_id, course_id)
);
```

The pair `(student_id, course_id)` is unique:

| student_id | course_id | enrollment_date |
|---:|---:|---|
| 101 | 201 | 2026-07-01 |
| 101 | 202 | 2026-07-01 |
| 102 | 201 | 2026-07-02 |

Student `101` may appear more than once, and course `201` may appear more than once. However, the same student cannot be enrolled in the same course twice because the combination must be unique.

## Composite Foreign Key Example

```sql
CREATE TABLE enrollment_results (
    student_id INT UNSIGNED NOT NULL,
    course_id INT UNSIGNED NOT NULL,
    marks DECIMAL(5, 2),
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_result_enrollment
        FOREIGN KEY (student_id, course_id)
        REFERENCES enrollments (student_id, course_id)
);
```

## Advantages

- Accurately represents relationships where uniqueness depends on several values.
- Prevents duplicate combinations.
- Avoids adding an artificial ID when the natural combination is meaningful.

## Limitations

- Foreign keys referencing the table must contain all key columns.
- Joins and indexes can be wider.
- Queries must often use multiple columns.
- Changing one part of the key can affect related tables.
- The design may become difficult if the composite key contains many columns.

## Composite Unique Key

A composite key does not always have to be the primary key. A table can have a single-column primary key and a separate composite unique constraint:

```sql
CREATE TABLE class_schedule (
    schedule_id INT PRIMARY KEY,
    room_id INT NOT NULL,
    class_date DATE NOT NULL,
    start_time TIME NOT NULL,
    CONSTRAINT uq_room_schedule
        UNIQUE (room_id, class_date, start_time)
);
```

This prevents two classes from using the same room at the same date and time.

# 8. Practical MySQL Constraints

The most important MySQL constraints for this chapter are:

```sql
PRIMARY KEY
FOREIGN KEY
UNIQUE
```

A **constraint** is a rule enforced by the database to protect data correctness.

## 8.1 `PRIMARY KEY`

### Single-Column Primary Key

```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);
```

### Named Primary Key

```sql
CREATE TABLE courses (
    course_id INT NOT NULL,
    course_name VARCHAR(100) NOT NULL,
    CONSTRAINT pk_courses PRIMARY KEY (course_id)
);
```

### Composite Primary Key

```sql
CREATE TABLE course_offerings (
    course_id INT NOT NULL,
    semester VARCHAR(20) NOT NULL,
    instructor_id INT NOT NULL,
    CONSTRAINT pk_course_offerings
        PRIMARY KEY (course_id, semester)
);
```

## 8.2 `FOREIGN KEY`

### Basic Foreign Key

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(100) NOT NULL,
    department_id INT,
    CONSTRAINT fk_students_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
);
```

### Foreign Key with Actions

```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
);
```

## 8.3 `UNIQUE`

A `UNIQUE` constraint prevents duplicate non-`NULL` values in a column or column combination.

### Single-Column Unique Constraint

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(254) NOT NULL,
    CONSTRAINT uq_users_username UNIQUE (username),
    CONSTRAINT uq_users_email UNIQUE (email)
);
```

### Composite Unique Constraint

```sql
CREATE TABLE course_registrations (
    registration_id INT PRIMARY KEY,
    student_id INT NOT NULL,
    course_id INT NOT NULL,
    CONSTRAINT uq_student_course UNIQUE (student_id, course_id)
);
```

This allows a student and course to appear many times separately, but prevents the same pair from appearing twice.

### Adding a Unique Constraint to an Existing Table

```sql
ALTER TABLE users
ADD CONSTRAINT uq_users_email UNIQUE (email);
```

### Removing a Unique Constraint

In MySQL, a unique constraint is represented by a unique index. You can remove it using its index name:

```sql
ALTER TABLE users
DROP INDEX uq_users_email;
```

Check the exact index name with:

```sql
SHOW CREATE TABLE users;
```

or:

```sql
SHOW INDEX FROM users;
```

# 9. Primary Key vs Unique Key

Both primary keys and unique keys prevent duplicate values, but they have different purposes and rules.

| Feature | Primary Key | Unique Key |
|---|---|---|
| Main purpose | Main identifier for each row | Enforces uniqueness for another candidate key |
| Number per table | Only one primary key | Multiple unique keys allowed |
| `NULL` values | Not allowed | MySQL can allow `NULL`, depending on the column definition and values |
| Identifies the table's rows | Yes, by definition | Can uniquely identify rows but is not the selected primary identifier |
| Foreign key target | Commonly referenced | Can be referenced when it satisfies the database requirements |
| Role in design | Selected main candidate key | Usually represents an alternate key |
| Example | `student_id PRIMARY KEY` | `email UNIQUE` |

## Example

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    email VARCHAR(254) UNIQUE,
    student_name VARCHAR(100) NOT NULL
);
```

- `student_id` is the main identity of the row.
- `email` must not be duplicated, but it is not the primary key.

## `NULL` and Unique Keys

A unique constraint generally permits multiple `NULL` values in MySQL because `NULL` means unknown and `NULL` values are not treated as equal in the ordinary comparison sense.

If every email must be present and unique, write:

```sql
email VARCHAR(254) NOT NULL UNIQUE
```

Do not rely on `UNIQUE` alone when the value is required.

# 10. Primary Key vs Foreign Key

| Feature | Primary Key | Foreign Key |
|---|---|---|
| Purpose | Identifies a row in its own table | Refers to a row in another table |
| Location | Parent or any independent table | Usually child or referencing table |
| Duplicate values | Not allowed | Usually allowed because many child rows may refer to one parent |
| `NULL` values | Not allowed | May be allowed if the relationship is optional |
| Number per table | One primary key constraint | Multiple foreign keys allowed |
| Creates | Entity identity | A relationship between tables |
| Example | `customers.customer_id` | `orders.customer_id` |

## Example

```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id)
);
```

Here:

- `customers.customer_id` is the primary key.
- `orders.order_id` is the primary key of `orders`.
- `orders.customer_id` is a foreign key.
- Multiple orders can have the same `customer_id`.
- Every non-null `orders.customer_id` must refer to an existing customer.

# 11. Candidate Key vs Primary Key

| Feature | Candidate Key | Primary Key |
|---|---|---|
| Meaning | Any minimal key that can uniquely identify rows | The candidate key selected as the main identifier |
| Number per table | Zero or more conceptually; normally one or more if a relation has a suitable identifier | Exactly one primary key constraint at most |
| Selection | A possible choice | The chosen key |
| Implementation | Often represented by `UNIQUE` and `NOT NULL` | Implemented using `PRIMARY KEY` |
| Example | `student_id`, `email` | `student_id` chosen as primary key |

## Example

Suppose these columns are unique:

- `employee_id`
- `employee_number`
- `email`

All three may be candidate keys. If the designer selects `employee_id` as the primary key:

- `employee_id` becomes the primary key.
- `employee_number` becomes an alternate key.
- `email` becomes an alternate key.

## Selection Principle

A primary key should normally be selected from the candidate keys. It should be unique, stable, simple, and suitable for references from other tables.

# 12. Composite Key vs Primary Key

These concepts are related but describe different properties.

- **Primary key** describes the role of a key: it is the selected main identifier.
- **Composite key** describes the structure of a key: it contains multiple columns.

Therefore, a primary key can be:

- A single-column primary key
- A composite primary key

## Single-Column Primary Key

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL
);
```

## Composite Primary Key

```sql
CREATE TABLE order_items (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

The pair `(order_id, product_id)` identifies one product line in one order.

| Feature | Composite Key | Primary Key |
|---|---|---|
| Describes | A key containing multiple columns | The selected main key of a table |
| Number of columns | Two or more | One or more |
| Can be used together? | Yes | Yes, a primary key can be composite |
| Example | `(student_id, course_id)` | `student_id` or `(student_id, course_id)` |
| Main concern | Combined values must be unique | Every row must have a unique, non-null identity |

## When to Use a Composite Primary Key

Use a composite primary key when:

- The relationship itself is identified by multiple values.
- No single column naturally identifies a row.
- The combination has clear and stable meaning.
- Related tables can conveniently reference all components.

Consider a surrogate single-column ID when:

- The composite key would contain many columns.
- Many other tables need to reference the row.
- The natural values may change.
- A simpler reference is beneficial for the application.

# 13. Complete Practical Example

The following example uses primary, foreign, unique, and composite keys together.

```sql
CREATE DATABASE IF NOT EXISTS key_demo_db;
USE key_demo_db;

CREATE TABLE departments (
    department_id INT UNSIGNED AUTO_INCREMENT,
    department_code CHAR(5) NOT NULL,
    department_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (department_id),
    CONSTRAINT uq_departments_code UNIQUE (department_code),
    CONSTRAINT uq_departments_name UNIQUE (department_name)
);

CREATE TABLE students (
    student_id INT UNSIGNED AUTO_INCREMENT,
    student_number VARCHAR(20) NOT NULL,
    email VARCHAR(254) NOT NULL,
    student_name VARCHAR(100) NOT NULL,
    department_id INT UNSIGNED NOT NULL,
    PRIMARY KEY (student_id),
    CONSTRAINT uq_students_number UNIQUE (student_number),
    CONSTRAINT uq_students_email UNIQUE (email),
    CONSTRAINT fk_students_department
        FOREIGN KEY (department_id)
        REFERENCES departments (department_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
);

CREATE TABLE courses (
    course_id INT UNSIGNED AUTO_INCREMENT,
    course_code VARCHAR(20) NOT NULL,
    course_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (course_id),
    CONSTRAINT uq_courses_code UNIQUE (course_code)
);

CREATE TABLE enrollments (
    student_id INT UNSIGNED NOT NULL,
    course_id INT UNSIGNED NOT NULL,
    enrollment_date DATE NOT NULL,
    grade CHAR(2),
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_enrollments_student
        FOREIGN KEY (student_id)
        REFERENCES students (student_id)
        ON DELETE CASCADE,
    CONSTRAINT fk_enrollments_course
        FOREIGN KEY (course_id)
        REFERENCES courses (course_id)
        ON DELETE CASCADE
);
```

## What This Example Demonstrates

- `departments.department_id` is a primary key.
- `department_code` and `department_name` are unique alternate keys.
- `students.student_id` is a primary key.
- `student_number` and `email` are alternate keys enforced with `UNIQUE`.
- `students.department_id` is a foreign key.
- `courses.course_id` is a primary key.
- `enrollments` uses a composite primary key: `(student_id, course_id)`.
- `enrollments.student_id` and `enrollments.course_id` are foreign keys.
- `ON DELETE CASCADE` removes enrollments when the related student or course is deleted.
- `ON DELETE RESTRICT` prevents deletion of a department while students still refer to it.

# 14. Inspecting Keys in MySQL

## View the Table Definition

```sql
SHOW CREATE TABLE students;
```

This displays primary keys, foreign keys, unique constraints, indexes, and column definitions.

## View Indexes

```sql
SHOW INDEX FROM students;
```

This shows indexes created for primary and unique keys, among other indexes.

## View Columns and Key Flags

```sql
DESCRIBE students;
```

The `Key` column may show:

- `PRI`: Primary key
- `UNI`: Unique index
- `MUL`: Non-unique index or a column that can contain repeated indexed values

## Query Constraint Metadata

For more detailed inspection:

```sql
SELECT
    TABLE_NAME,
    CONSTRAINT_NAME,
    CONSTRAINT_TYPE
FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = DATABASE();
```

To inspect foreign key relationships:

```sql
SELECT
    TABLE_NAME,
    CONSTRAINT_NAME,
    COLUMN_NAME,
    REFERENCED_TABLE_NAME,
    REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND REFERENCED_TABLE_NAME IS NOT NULL;
```

# 15. Key Design Best Practices

- Every important table should have a reliable primary key.
- Keep primary keys stable; changing them can affect foreign keys and application code.
- Choose a key that is unique and available for every row.
- Use `NOT NULL` with values that are required.
- Use `UNIQUE` for alternate identifiers such as email or business numbers.
- Use foreign keys to enforce real relationships instead of relying only on application code.
- Match foreign key data types with the referenced key, including signedness for integers.
- Name constraints clearly, such as `pk_students`, `fk_orders_customer`, and `uq_users_email`.
- Use composite keys when the combination naturally identifies the row.
- Do not add unnecessary columns to a key.
- Avoid using changeable information as the primary key when a stable identifier is available.
- Be careful with `ON DELETE CASCADE`; it can remove many related rows automatically.
- Check indexes and query patterns when choosing a key.
- Review dependencies before renaming or removing a key.

# 16. Common Mistakes

## Mistake 1: Using a Name as the Primary Key

Names are often duplicated and can change. Use a stable identifier such as an ID instead.

## Mistake 2: Assuming a Foreign Key Must Be Unique

A foreign key usually allows duplicates because many child rows can refer to one parent.

Example: one customer can place many orders.

## Mistake 3: Treating `UNIQUE` as Identical to `PRIMARY KEY`

A table can have multiple unique constraints but only one primary key. Unique columns may allow `NULL` unless they are also declared `NOT NULL`.

## Mistake 4: Mismatching Foreign Key Types

These definitions may cause problems:

```sql
parent_id INT UNSIGNED
child_parent_id INT
```

Use compatible definitions, preferably:

```sql
parent_id INT UNSIGNED
child_parent_id INT UNSIGNED
```

## Mistake 5: Creating a Foreign Key Before the Parent Table

Create the referenced table first, then create the table containing the foreign key.

## Mistake 6: Using `ON DELETE CASCADE` Without Understanding It

Deleting one parent row can delete many child rows. Use it only when this behavior is intended.

## Mistake 7: Making a Composite Key Too Wide

A composite key with many large text columns can make indexes and foreign keys inefficient. Consider a stable surrogate ID plus a suitable unique constraint if necessary.

## Mistake 8: Assuming Auto-Increment Values Cannot Have Gaps

Deleted rows, failed inserts, and transaction behavior can produce gaps. Auto-increment values are identifiers, not row counts.

# 18. Final Revision Summary

- A **super key** is any attribute set that uniquely identifies a row.
- A **candidate key** is a minimal super key.
- A **primary key** is the candidate key chosen as the main row identifier.
- A **foreign key** refers to a key in another table and enforces referential integrity.
- An **alternate key** is a candidate key not selected as the primary key.
- A **composite key** contains two or more columns.
- A primary key can be single-column or composite.
- A table has at most one primary key constraint but can have multiple unique constraints.
- Primary keys cannot be `NULL`.
- Foreign keys can usually repeat because many child rows may refer to one parent.
- A `UNIQUE` constraint prevents duplicate values and commonly implements alternate keys.
- `FOREIGN KEY ... REFERENCES` connects related tables.
- Composite keys are useful when a combination, such as `(student_id, course_id)`, identifies a relationship.
- Use `SHOW CREATE TABLE`, `SHOW INDEX`, and `DESCRIBE` to inspect keys in MySQL.
- Keys are essential for identity, uniqueness, relationships, data integrity, and reliable database design.
